# 5\.长期记忆机制设计

可以。现在我们讨论的 **5\. 长期记忆机制**，它和上一节“会话摘要”不一样：

> **会话摘要**：只属于当前 conversation，用来压缩本会话历史。
> **长期记忆**：跨 conversation 保存用户偏好、长期目标、项目状态，让新会话也能用。
>
>

你前面这套系统本来就把“长期记忆机制”定义为解决跨会话保存用户偏好和项目状态，重点包括记什么、不记什么、手动保存还是自动抽取、记忆分类、删除、冲突和注入数量限制。

# 长期记忆机制的定位

我建议定义为：

```Plain Text
User Memory / Long-term Memory
```

中文叫：

```Plain Text
用户长期记忆
```

它的作用是：

```Plain Text
跨会话保存对未来回答有持续价值的信息，
在 Agent Memory Mode 下选择性注入 prompt。
```

它不是：

```Plain Text
不是聊天记录全文
不是 conversation summary
不是知识库文档
不是自动保存一切用户说过的话
```

你要把它设计得很克制。

# 记什么？

长期记忆只记 **长期稳定、未来经常有用** 的信息。

我建议第一版记这几类：

## 2\.1 用户偏好 PREFERENCE

例如：

```Plain Text
用户希望回答先给结论，再解释原因。
用户更关注求职和面试包装角度。
用户喜欢中文回答。
用户希望技术解释不要太抽象，要结合项目。
```

这类适合长期保存。

---

## 2\.2 项目状态 PROJECT\_STATE

例如：

```Plain Text
用户当前主项目是 DocPilot。
DocPilot 当前正在设计会话级上下文管理系统。
当前已确定默认 RECENT_TURNS，可选 AGENT_MEMORY。
```

这类对项目协作有用。

但注意：项目状态会变化，所以要允许更新和覆盖。

---

## 2\.3 长期目标 TASK\_GOAL

例如：

```Plain Text
用户希望用 DocPilot 投 Java 后端 / AI 应用 / Agent 开发实习。
用户希望项目亮点能支撑简历和面试。
```

这类能帮助后续回答更贴合目标。

---

## 2\.4 技术栈 / 工作习惯 TECH\_CONTEXT

例如：

```Plain Text
用户项目技术栈是 Spring Boot + MySQL + Redis + RocketMQ + MinIO + Qdrant。
用户用 Codex CLI 在本地改代码、跑测试、commit。
```

你项目环境里也明确了本地 Windows 开发、Codex CLI 改代码跑测试、网页端 GPT 负责定方向和审查计划等边界。

这类长期上下文对后续协作很有用。

# 不记什么？

这个非常重要。不要让长期记忆变成隐私黑洞。

第一版明确不记：

```Plain Text
短期情绪
临时吐槽
一次性问题
完整聊天记录
完整 prompt
API key / token / 密码 / SSH 信息
数据库连接串
身份证、手机号、住址等敏感信息
未经确认的健康、政治、宗教等敏感属性
```

尤其是你的项目安全边界里已经明确：不要上传 `.env`、API key、SSH 信息、数据库密码、真实 token，也不要公开真实服务器 IP。
 所以 memory 里也必须避免保存这些东西。

# 用户手动保存还是自动抽取？

我建议第一版：

> **以用户手动保存为主，自动抽取暂时不做或只做候选建议。**
>
>

也就是用户明确说：

```Plain Text
记住这个
以后都按这个风格回答
把这个保存到项目记忆
```

系统才保存。

这样好处是：

```Plain Text
安全
可控
容易实现
面试好解释
不会乱记敏感信息
```

自动抽取虽然更像 ChatGPT，但第一版风险较高：

```Plain Text
容易误记
容易保存敏感信息
需要冲突处理
需要用户确认机制
需要更复杂的召回和删除逻辑
```

所以推荐路线：

```Plain Text
MVP：用户手动保存
增强版：模型提出“是否保存为记忆”的建议
高级版：自动抽取 + 用户确认
```

不要第一版就自动保存一切。

# 记忆分类怎么设计？

建议 memory\_type 用枚举：

```Plain Text
PREFERENCE        用户偏好
PROJECT_STATE     项目状态
TASK_GOAL         长期目标
TECH_CONTEXT      技术上下文
ANSWER_STYLE      回答风格
CUSTOM            用户自定义
```

每条 memory 还要有状态：

```Plain Text
ACTIVE
ARCHIVED
DELETED
```

其中：

```Plain Text
ACTIVE：可注入 prompt
ARCHIVED：保留但默认不注入
DELETED：逻辑删除，不再注入
```

# 数据表设计

建议新增：

```Plain Text
tb_user_memory
```

字段：

```Plain Text
id
user_id
memory_type
content
source_type          // USER_MANUAL / SYSTEM_SUGGESTED / IMPORTED
source_conversation_id
source_message_id
status               // ACTIVE / ARCHIVED / DELETED
priority             // 1-100
confidence           // 第一版可默认 1.0
last_used_time
use_count
create_time
update_time
```

几个关键字段解释：

```Plain Text
user_id：权限隔离
memory_type：分类
source_type：区分用户手动保存还是系统建议
status：支持删除和归档
priority：决定注入优先级
last_used_time/use_count：后续做记忆淘汰或排序
```

第一版可以不做 embedding 检索，只按类型和 priority 取最近/最重要的几条。

# 记忆删除怎么做？

必须支持用户删除。

删除建议做软删除：

```Plain Text
ACTIVE -> DELETED
```

删除后要求：

```Plain Text
不再注入 prompt
不再出现在普通 memory 列表
审计上可以保留 delete_time
```

API 可以设计：

```Plain Text
GET /api/memories
POST /api/memories
PATCH /api/memories/{id}
DELETE /api/memories/{id}
```

删除时只允许删除自己的 memory：

```Plain Text
where id = ? and user_id = currentUserId
```

# 记忆冲突怎么处理？

这是面试很容易问的点。

例如旧记忆：

```Plain Text
用户希望回答简短。
```

新记忆：

```Plain Text
用户希望详细解释。
```

这就冲突。

第一版不要做复杂推理，可以用简单规则：

```Plain Text
同类型记忆，新记忆优先
用户当前问题优先于长期记忆
手动保存优先于系统建议
ACTIVE 优先于 ARCHIVED
```

Prompt 里也要写清楚：

```Plain Text
如果长期记忆与当前用户问题冲突，以当前用户问题为准。
```

长期记忆只作为默认偏好，当用户当前输入有明确要求时，以当前输入为准。



# 记忆注入数量限制

不要把所有 memory 都塞进 prompt。

建议第一版限制：

```Plain Text
最多注入 3～5 条 memory
总 token 不超过 500～800
```

排序规则：

```Plain Text
1. 和当前 conversation 绑定项目相关的 PROJECT_STATE
2. 用户回答风格 PREFERENCE / ANSWER_STYLE
3. 当前任务目标 TASK_GOAL
4. 最近更新的 TECH_CONTEXT
```

如果是普通 RECENT\_TURNS 模式：

```Plain Text
不注入 memory
```

只有 AGENT\_MEMORY 模式才注入。

# Memory 和 Summary 怎么区分？

这个一定要讲清楚。

一句话：

```Plain Text
summary 记“这次聊到哪了”；
memory 记“这个用户长期是什么偏好和目标”；
knowledge base 记“外部资料里有什么证据”。
```

# Prompt 注入格式

建议格式化，不要散乱拼接：

```Plain Text
[User Memories]
- PREFERENCE: 用户希望回答先给结论，再给工程原因。
- PROJECT_STATE: 用户当前主项目是 DocPilot，正在设计 Agent Memory Mode。
- TASK_GOAL: 用户希望项目能用于 Java 后端 / AI 应用实习求职。

Rules:
- 如果 memory 与当前问题冲突，以当前问题为准。
- 不要根据 memory 推断用户未明确表达的敏感属性。
```

这样模型更容易理解这些信息的边界。

# 第一版 MVP 建议

第一版就做这些：

```Plain Text
1. 新增 tb_user_memory
2. 支持用户手动保存 memory
3. 支持 memory 分类
4. 支持查看 / 删除 memory
5. 只在 AGENT_MEMORY 模式下注入 memory
6. 每次最多注入 3～5 条
7. DELETED memory 不注入
8. 不保存 secrets / 敏感信息
9. 当前问题优先于长期记忆
```

暂时不做：

```Plain Text
自动抽取记忆
memory embedding 检索
复杂冲突合并
记忆重要性模型
跨用户共享记忆
敏感信息自动识别大模型审核
```

# 测试重点

需要覆盖：

```Plain Text
用户可以创建 memory
用户只能查看自己的 memory
用户不能删除别人的 memory
DELETED memory 不会注入 prompt
RECENT_TURNS 模式不注入 memory
AGENT_MEMORY 模式注入 ACTIVE memory
注入数量不超过限制
当前问题与 memory 冲突时 prompt 规则正确
memory 中不返回敏感字段
```

如果后续接知识库，RAG 仍然要走已有的权限隔离。DocPilot 的 RAG 路线本身已经强调 metadata filter、citation、Agent Trace / eval 等工程链路，长期记忆不能绕过这些已有的 scope guard。

# 面试怎么讲？

你可以这样说：

> 我把长期记忆和会话摘要分开设计。会话摘要只压缩当前 conversation，而长期记忆是跨会话保存用户偏好、任务目标和项目状态。第一版采用用户显式保存记忆，避免自动抽取导致隐私和误记问题；记忆按 PREFERENCE、PROJECT\_STATE、TASK\_GOAL 等类型分类，支持查看、删除和软删除。Agent Memory Mode 下最多注入 3～5 条 ACTIVE memory，并且当前用户问题优先于长期记忆，防止旧记忆污染回答。
>
>

---

# 一句话定方案

我建议长期记忆机制这样定：

> **第一版只做用户显式长期记忆：保存用户偏好、项目状态、长期目标和技术上下文；支持分类、查看、删除和注入数量限制；只在 Agent Memory Mode 下使用，且当前问题优先于记忆，避免隐私风险和旧记忆污染。**
>
>
