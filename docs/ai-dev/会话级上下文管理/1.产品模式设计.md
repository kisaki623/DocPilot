# 1\.产品模式设计

# 会话模式

## 模式一：标准对话

英文内部名：

```Plain Text
RECENT_TURNS
```

用户看到的名字：

```Plain Text
标准对话
```

说明文案：

```Plain Text
适合临时问答和普通聊天，只参考最近几轮对话，速度快、成本低。
```

它的上下文来源：

```Plain Text
系统提示词
+ 最近 N 轮消息
+ 当前问题
```

适合场景：

```Plain Text
解释一个概念
修改一句话
继续说
换成面试版
总结短一点
临时问代码问题
```

这个模式是默认模式。

## 模式二：Agent 记忆会话

英文内部名

AGENT\_MEMORY

用户看到的名字：

```Plain Text
Agent 记忆对话
```

说明文案：

```Plain Text
适合长期任务、项目协作和知识库问答，会结合最近对话、会话摘要、已保存记忆和绑定知识库。
```

它的上下文来源：

```Plain Text
系统提示词
+ 用户显式记忆
+ 当前会话摘要
+ 最近 N 轮消息
+ 可选知识库 RAG evidence
+ 当前问题
```

适合场景：

```Plain Text
长期做一个项目
连续准备面试
围绕一个知识库持续问答
根据之前的项目状态继续推进
让 AI 记住用户偏好和任务目标
```



# 创建对话时选择，创建后固定

我建议这样设计：

```Plain Text
新建对话时选择模式
创建后默认固定
标准对话可以升级为 Agent 记忆对话
Agent 记忆对话不建议降级，想要干净上下文就新建标准对话
```

原因是上下文模式不只是前端展示，它会影响后端很多行为：

```Plain Text
是否生成会话摘要
是否读取 user_memory
是否绑定 knowledgeBase
是否触发 RAG
是否记录 context trace
token 预算怎么分配
```

如果允许每条消息随便切换，状态会复杂很多。

所以产品上建议：

```Plain Text
模式是 conversation 级别，不是 message 级别。
```

# 新建对话页面怎么设计？

新建对话时给用户两个卡片：

```Plain Text
标准对话
适合普通问答，只参考最近几轮，成本低、回答更轻量。

Agent 记忆对话
适合长期任务，会参考会话摘要、已保存记忆和绑定知识库。
```

默认选中：

```Plain Text
标准对话
```

Agent 记忆对话下面可以有可选项：

```Plain Text
绑定知识库：可选
是否启用已保存记忆：默认开启
是否生成会话摘要：默认开启
```

但第一版不要做太复杂，先做：

```Plain Text
选择模式
可选绑定知识库
```

就够了。

# 对话内应该怎么展示模式？

在聊天页顶部展示一个小标签：

```Plain Text
当前模式：标准对话
```

或者：

```Plain Text
当前模式：Agent 记忆对话
已启用：会话摘要 / 长期记忆 / 知识库
```

Agent 记忆对话里可以有一个“本轮上下文来源”按钮，点开看到：

```Plain Text
最近消息：8 条
会话摘要：已使用
长期记忆：3 条
知识库 evidence：4 条
```

这个设计很重要。因为它能体现你的系统不是黑盒，而是可解释的上下文管理。

DocPilot 当前路线本身就强调 Agent Trace / eval 记录、citations、debug snapshot 这类可观测能力，所以上下文来源展示和项目风格是匹配的。

# Agent 记忆对话里，不是所有问题都走 RAG

这个一定要设计清楚。

Agent Memory Mode 不是等于“每次都 RAG”。

它应该是：

```Plain Text
普通追问：只用最近多轮 + 摘要 + 记忆
资料相关问题：再触发知识库 RAG
```

比如：

```Plain Text
用户：继续说
```

这种不需要 RAG。

但如果用户问：

```Plain Text
结合这个知识库里的文档总结一下
```

才走：

```Plain Text
query rewrite
+ knowledgeBase retrieval
+ evidence prompt
```

所以产品逻辑应该是：

```Plain Text
Agent Memory Mode = 上下文增强模式
RAG = 其中一个可触发的资料检索能力
```

不要把二者混为一谈。

# 我会删掉或延后的东西

第一版不建议做这些：

```Plain Text
全量历史模式
每条消息自由切换模式
自动抽取所有长期记忆
复杂记忆冲突解决
多 Agent 记忆共享
记忆向量检索
前端复杂记忆管理中心
```

这些不是不能做，而是现在做会拖慢主线。

你的项目开发环境也明确：网页端 GPT 主要负责定方向、拆任务、审查 Plan；代码修改、测试和 commit 交给本地 Codex CLI；安全上不上传 \.env、API key、SSH 信息，本地单测不强依赖远程服务器。

所以这个功能也应该先做可测试、可控、边界清楚的 MVP，而不是一下子做成复杂平台。

# 第一版 MVP 我建议做到这个程度

第一版只做：

```Plain Text
1. 新建对话时选择：标准对话 / Agent 记忆对话
2. conversation.contextMode 固定
3. 标准对话只取最近 N 轮
4. Agent 记忆对话取最近 N 轮 + 会话摘要
5. Agent 记忆对话允许绑定 knowledgeBase
6. 资料相关问题才触发知识库 RAG
7. 展示本轮使用的上下文来源
```

长期记忆 `user_memory` 可以放到第二阶段：

```Plain Text
用户手动保存记忆
查看已保存记忆
删除记忆
Agent 记忆对话注入最多 3～5 条记忆
```

原因是“长期记忆”涉及隐私和删除逻辑，第一版可以先把模式和会话摘要跑通。
