# 6\.知识库绑定与RAG融合

我们现在讨论 **6\. 知识库绑定与 RAG 融合**。这一节的核心是：

> **Agent Memory Mode 不只是“记住用户偏好”，还要能绑定某个知识库，在需要资料依据时自动检索知识库，把 RAG evidence 和 memory、summary、recent turns 一起拼进 prompt。**
>
>

你前面的设计路线里，这一节主要要解决：一个会话是否绑定 `knowledgeBaseId`、什么时候触发 RAG、什么时候只用最近多轮、RAG evidence 如何和 memory 一起拼 prompt、知识库权限如何校验。

# 先定义这个能力

我建议叫：

```Plain Text
KnowledgeBase-bound Agent Memory
```

中文可以叫：

```Plain Text
知识库绑定型 Agent 记忆对话
```

它的含义是：

```Plain Text
一个 Agent Memory 会话可以绑定一个 knowledgeBaseId。
当用户问题需要资料依据时，系统会在该知识库内做 RAG 检索。
检索结果作为 evidence 注入 prompt。
如果问题不需要资料依据，就只用 memory + summary + recent turns。
```

也就是说：

```Plain Text
Agent Memory Mode = 长期记忆 + 会话摘要 + 最近多轮 + 可选知识库 RAG
```

# 会话是否应该绑定 knowledgeBaseId？

我建议：**可以绑定，但不是所有会话都必须绑定。**

`conversation` 表里可以有：

```Plain Text
bound_knowledge_base_id
```

为空表示：

```Plain Text
这个会话没有绑定知识库。
Agent Memory Mode 只使用 memory + summary + recent turns。
```

不为空表示：

```Plain Text
这个会话绑定了某个知识库。
当问题需要资料依据时，优先从该知识库检索 evidence。
```

这样设计比较灵活。

# 绑定时机怎么设计？

我建议有 3 种方式。

## 3\.1 创建会话时绑定

用户创建 Agent Memory 会话时选择：

```Plain Text
会话模式：Agent Memory Mode
绑定知识库：DocPilot 项目资料库
```

适合项目协作类场景。

比如：

```Plain Text
我创建一个 DocPilot 项目助手会话。
这个会话之后默认围绕 DocPilot 知识库回答。
```

---

## 3\.2 会话中手动绑定

用户在会话设置里选择：

```Plain Text
绑定知识库
```

或者发送：

```Plain Text
把这个会话绑定到 DocPilot 知识库
```

后端校验知识库属于当前用户，然后更新：

```Plain Text
conversation.bound_knowledge_base_id = kbId
```

---

## 3\.3 从文档 / 知识库页面进入自动绑定

比如用户在知识库详情页点击：

```Plain Text
开始问答
```

系统自动创建：

```Plain Text
contextMode = AGENT_MEMORY
boundKnowledgeBaseId = 当前知识库 ID
```

这个产品体验最好。

# 是否允许更换绑定知识库？

第一版建议：

> **允许手动更换，但要记录 trace；不要自动乱切。**
>
>

因为知识库一换，回答依据就变了。

建议规则：

```Plain Text
同一个会话默认只绑定一个知识库。
用户可以手动更换绑定知识库。
更换后从下一轮消息开始生效。
历史回答不重新解释。
```

如果用户需要完全干净的知识库上下文，建议新建会话。

不要做：

```Plain Text
系统根据问题自动在多个知识库之间切换。
```

这个会增加权限、解释性和检索复杂度。

# 什么时候触发 RAG？

这是本节最重要的问题。

我的建议是：

> **绑定知识库不等于每轮都检索。**
>
>

即使会话绑定了知识库，也要判断当前问题是否需要资料证据。

---

## 5\.1 不触发 RAG 的问题

这些只用：

```Plain Text
memory + summary + recent turns
```

例如：

```Plain Text
继续说
换成面试版
这句话优化一下
你刚才第二点展开
这个方案合理吗
给我总结我们刚刚讨论的内容
```

这些问题的答案主要来自当前对话上下文，不需要查知识库。

---

## 5\.2 触发 RAG 的问题

这些需要知识库 evidence：

```Plain Text
根据知识库回答
结合文档内容说明
资料里怎么说
这个项目文档目前状态是什么
这几篇文档分别讲了什么
从知识库里找依据
总结这个资料集
```

如果用户明确说：

```Plain Text
根据文档
结合知识库
从资料里
```

那就必须触发 RAG。

---

## 5\.3 模糊问题如何处理？

比如用户问：

```Plain Text
这个功能现在做到哪了？
```

如果会话绑定的是 DocPilot 项目知识库，那么这个问题很可能需要查知识库。

可以采用规则：

```Plain Text
AGENT_MEMORY + boundKnowledgeBaseId 不为空
并且问题涉及“项目状态 / 文档内容 / 资料 / 当前进度 / 已完成 / 路线”
则触发 RAG。
```

第一版用规则即可，不要一上来用 LLM intent classification。

# RAG 触发策略建议

可以定义一个枚举：

```Plain Text
RagTriggerMode
```

取值：

```Plain Text
AUTO
ALWAYS
NEVER
```

放在 conversation 上：

```Plain Text
rag_trigger_mode
```

推荐默认：

```Plain Text
AUTO
```

含义：

```Plain Text
AUTO：根据问题意图判断是否检索
ALWAYS：每轮都检索绑定知识库
NEVER：即使绑定知识库，也不自动检索
```

第一版甚至可以只做：

```Plain Text
AUTO
```

但在设计上预留枚举会更清晰。

# RAG evidence 如何和 memory 一起拼 prompt？

这是上下文拼接的关键。

我建议顺序是：

```Plain Text
System Prompt
+ Mode Instruction
+ User Memories
+ Conversation Summary
+ Recent Turns
+ KnowledgeBase RAG Evidence
+ Current User Message
```

为什么 RAG evidence 放在 recent turns 后面？

因为：

```Plain Text
memory / summary / recent turns 先交代用户目标和当前对话背景；
RAG evidence 紧贴当前问题，作为回答依据；
current message 最后出现，确保模型聚焦当前请求。
```

# Prompt 里如何区分 memory 和 evidence？

必须明确告诉模型：

```Plain Text
Memory 是用户偏好和项目背景，不一定是事实证据。
Evidence 是知识库检索结果，回答文档问题时必须以 evidence 为准。
```

推荐 prompt 格式：

```Plain Text
[User Memories]
- PREFERENCE: 用户希望回答先给结论，再解释工程原因。
- PROJECT_STATE: 用户当前主项目是 DocPilot。

[Conversation Summary]
本会话正在设计 Agent Memory Mode 的知识库绑定与 RAG 融合。

[Recent Turns]
user: ...
assistant: ...

[Knowledge Base Evidence]
[1] documentTitle=ROADMAP_RAG.md, documentId=83, chunkIndex=4, score=0.82
内容：......

[2] documentTitle=上下文会话系统设计路线.md, documentId=91, chunkIndex=2, score=0.79
内容：......

[Current Question]
开始设计知识库绑定与 RAG 融合。
```

再加规则：

```Plain Text
如果问题要求基于知识库回答，必须优先使用 Knowledge Base Evidence。
如果 evidence 不足，应说明证据不足，不要编造。
如果 memory 与 evidence 冲突，知识库事实问题以 evidence 为准。
如果 memory 与当前问题冲突，以当前问题为准。
```

# 知识库权限怎么校验？

这是必须做硬的地方。

绑定知识库时要校验：

```Plain Text
knowledgeBase.userId == currentUserId
```

每次检索时也要校验：

```Plain Text
conversation.userId == currentUserId
conversation.boundKnowledgeBaseId 属于 currentUserId
knowledgeBase ACTIVE
knowledgeBase 下 ACTIVE 文档属于 currentUserId
```

你的 T011 设计里已经有 `KnowledgeBaseScopeGuard`，它负责校验 owner、文档归属，并且 `listActiveKnowledgeBaseDocuments` 只返回 ACTIVE 成员。

所以 Agent Memory Mode 不应该自己绕过这套 guard，而应该复用：

```Plain Text
KnowledgeBaseScopeGuard
KnowledgeBaseRagRetrievalService
KnowledgeBaseRagQaService
```

不要直接查 Qdrant。

# RAG 检索应该怎么走？

Agent Memory Mode 里如果触发 RAG，流程应该是：

```Plain Text
1. 获取 currentUserId
2. 读取 conversation
3. 校验 conversation 属于 currentUserId
4. 读取 boundKnowledgeBaseId
5. 判断是否需要 RAG
6. 调用 KnowledgeBaseRagRetrievalService
7. 通过 KnowledgeBaseScopeGuard 获取 ACTIVE documentIds
8. 使用 userId + documentIds + indexVersion 检索
9. 对 hits 做二次 scope 校验
10. 生成 evidence context
11. 拼入 prompt
```

T011b 的设计里，多文档 retrieval 本来就要求使用 `userId + documentIds + indexVersion` 检索，并对返回 hits 做二次校验：userId 匹配、documentId 属于 ACTIVE KB 文档、indexVersion 匹配。

这说明知识库绑定和 RAG 融合不能另起炉灶，应该复用 T011 的 retrieval 能力。

# no\-evidence 怎么处理？

如果触发了 RAG，但没找到证据：

```Plain Text
retrievalResult.noEvidence = true
```

那有两种策略。

## 普通知识库问答

如果用户明确要求：

```Plain Text
根据知识库回答
```

则应该返回：

```Plain Text
当前知识库中没有找到足够证据，无法基于知识库回答该问题。
```

不要调用大模型乱答。

---

## Agent Memory Mode 一般问题

如果问题不是强制“根据知识库”，只是系统自动触发了 RAG，但没有 evidence，可以降级为：

```Plain Text
不使用知识库 evidence
继续基于 memory + summary + recent turns 回答
并在 trace 中标记 noEvidence
```

例如用户问：

```Plain Text
这个方案合理吗？
```

RAG 没证据也可以回答设计建议。

所以需要区分：

```Plain Text
requiredRag = 用户明确要求基于知识库
optionalRag = 系统判断可能有帮助
```

规则：

```Plain Text
requiredRag no-evidence：返回 evidence 不足 fallback
optionalRag no-evidence：降级为 memory + recent turns
```

# 绑定知识库和长期记忆的边界

这点一定要讲清楚：

```Plain Text
长期记忆：用户偏好、项目目标、任务状态
知识库：文档事实、项目资料、外部证据
```

例如：

```Plain Text
用户希望面试化回答
```

这是 memory。

```Plain Text
ROADMAP_RAG.md 里写了 T005 是 RAG Retrieval + QA + SSE
```

这是 knowledge evidence。

不要把文档内容存进 user\_memory。

否则会出现：

```Plain Text
知识库更新了，但 memory 里还保存旧文档事实
```

所以：

```Plain Text
用户偏好进 memory
文档事实走 RAG
```

# 是否要把 RAG evidence 保存进会话历史？

建议保存“引用摘要”，不要保存完整 evidence。

可以在 assistant message 或 context trace 里记录：

```Plain Text
ragTriggered = true
knowledgeBaseId = 12
retrievalHitCount = 5
citationDocumentIds = [83, 84]
citationIndexes = [1, 2, 3]
```

不要保存完整 prompt。

如果要展示 citation，可以保存 citation response，但注意不要保存过长原文。

DocPilot RAG Roadmap 本身已经把 citation 和 Agent Trace / eval 作为主链路目标。

这里的 trace 也应该延续这个思路。

# 第一版 MVP 建议

第一版做这些就够：

```Plain Text
1. conversation 支持 boundKnowledgeBaseId
2. 绑定 / 解绑知识库时校验 owner
3. 只在 AGENT_MEMORY 模式下使用 boundKnowledgeBaseId
4. 用规则判断是否触发 RAG
5. 触发后调用现有 KnowledgeBaseRagRetrievalService
6. RAG evidence 拼到 prompt 中
7. no-evidence 区分 required / optional
8. context trace 记录 ragTriggered、evidenceCount、knowledgeBaseId
9. 不把知识库全文写入 user_memory
```

暂时不做：

```Plain Text
多知识库同时绑定
自动跨知识库选择
RAG evidence 长期保存
基于 memory embedding 召回知识库
MCP
复杂 reranker
```

# 测试重点

需要覆盖：

```Plain Text
AGENT_MEMORY 可以绑定自己的 knowledgeBase
绑定别人的 knowledgeBase 失败
RECENT_TURNS 模式不自动使用 knowledgeBase
AGENT_MEMORY + boundKnowledgeBaseId + 文档意图触发 RAG
普通追问不触发 RAG
required RAG no-evidence 返回 fallback
optional RAG no-evidence 降级为普通回答
RAG evidence 被拼进 prompt
memory 与 evidence 同时存在时顺序正确
deleted memory 不注入
REMOVED 文档不参与 retrieval
跨用户 KB 文档不被召回
context trace 记录 ragTriggered/evidenceCount
```

# 面试怎么讲？

你可以这样讲：

> 我把知识库绑定设计成 Agent Memory Mode 的增强能力。会话可以绑定一个 knowledgeBaseId，但不是每轮都检索。系统会先根据用户问题判断是否需要资料依据，普通追问只使用会话摘要、长期记忆和最近多轮；涉及“根据文档、结合知识库、资料里怎么说”的问题才触发知识库 RAG。触发后复用 KnowledgeBaseRagRetrievalService 和 KnowledgeBaseScopeGuard，使用 userId \+ documentIds \+ indexVersion 进行检索，并对 hits 做二次 scope 校验。Prompt 中明确区分 User Memory 和 Knowledge Evidence，文档事实以 evidence 为准，用户偏好以 memory 为准，避免把文档内容误存进长期记忆。
>
>

# 一句话定方案

我建议知识库绑定与 RAG 融合这样定：

> **Agent Memory Mode 可以绑定一个知识库；系统按意图决定是否触发 RAG，触发后复用 KnowledgeBaseRagRetrievalService 获取受权限保护的 evidence，并与 memory、summary、recent turns 共同拼接 prompt。长期记忆保存用户偏好和项目状态，知识库 RAG 提供文档事实证据，两者边界必须分开。**
>
>
