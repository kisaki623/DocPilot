# 11\.Trace/可观测性设计

开始 **11\. Trace / 可观测性设计**。

这一节的核心是：

> **让用户、开发者、面试官都能看懂：这次回答到底用了哪些上下文，是否用了长期记忆，是否用了会话摘要，是否触发 RAG，命中了哪些文档，是否发生了裁剪。**
>
>

前面我们设计了上下文拼接、摘要、长期记忆、知识库 RAG、权限和 token 预算。Trace 就是把这些过程用**脱敏、结构化、可展示**的方式记录下来。你之前的设计清单里也把 Trace 定义为：本轮使用了几条 recent messages、是否使用 summary、注入了哪些 memory 摘要、是否触发 RAG、命中了哪些文档、token 估算等。

---

# Trace 的定位

我建议把它定义为：

```Plain Text
Context Trace / Context Assembly Trace
```

中文叫：

```Plain Text
上下文构建轨迹
```

它不是日志全文，也不是 prompt 原文。

它的作用是回答这些问题：

```Plain Text
本轮是什么 contextMode？
用了几条最近消息？
用了没有会话摘要？
注入了几条长期记忆？
有没有触发 RAG？
RAG 命中了哪些文档？
估算 prompt token 多少？
哪些上下文被裁剪了？
有没有 no-evidence？
```

一句话：

> Trace 是“本轮上下文来源和处理过程的解释说明”。
>
>

---

# Trace 不能是什么？

这一点必须先定死。

Trace 不能记录：

```Plain Text
完整 prompt
完整长期记忆内容
完整会话摘要内容
完整 RAG evidence 原文
API key
Authorization
数据库连接串
服务器 IP
完整异常堆栈
用户敏感信息
```

因为 Trace 很可能要返回给前端展示，或者写入数据库用于调试。

你的项目环境边界里已经明确不能上传 `.env`、API key、SSH 信息、数据库密码、真实 token，也不能公开真实服务器 IP。
所以 Trace 必须是**脱敏摘要**，不是原始上下文快照。

---

# Trace 应该记录哪些信息？

我建议分成 7 类。

---

## 3\.1 基础信息

```JSON
{
  "traceId": "ctx_20260611_xxx",
  "conversationId": 1001,
  "messageId": 9002,
  "contextMode": "AGENT_MEMORY",
  "createdAt": "2026-06-11T10:00:00"
}
```

作用：

```Plain Text
定位是哪一次回答的上下文构建过程。
```

---

## 3\.2 会话上下文信息

```JSON
{
  "recentTurnCount": 8,
  "recentMessageCount": 16,
  "recentTurnTokens": 3200,
  "summaryUsed": true,
  "summaryVersion": 3,
  "summaryTokens": 900
}
```

作用：

```Plain Text
说明本轮用了多少最近对话，是否用了会话摘要。
```

---

## 3\.3 长期记忆信息

不要返回完整 memory 内容，只返回数量和类型。

```JSON
{
  "memoryUsed": true,
  "memoryCount": 4,
  "memoryTypes": ["PREFERENCE", "PROJECT_STATE", "TASK_GOAL"],
  "memoryTokens": 520
}
```

如果要展示给用户，可以展示简短 label，而不是完整内容：

```JSON
{
  "memoryBriefs": [
    {
      "memoryType": "PREFERENCE",
      "brief": "回答风格偏好"
    },
    {
      "memoryType": "PROJECT_STATE",
      "brief": "DocPilot 项目状态"
    }
  ]
}
```

---

## 3\.4 RAG 检索信息

如果触发了 RAG，记录：

```JSON
{
  "ragTriggered": true,
  "ragRequired": true,
  "knowledgeBaseId": 12,
  "retrievalTopK": 6,
  "evidenceCount": 5,
  "noEvidence": false,
  "documentHitCounts": {
    "ROADMAP_RAG.md": 2,
    "STATE.md": 1,
    "上下文会话系统设计路线.md": 2
  }
}
```

这里可以记录文档标题和命中数量，但不要把完整 chunk 内容放进 trace。

DocPilot RAG 主线本身就强调 citation、Agent Trace、eval 记录等能力，所以这里的 Trace 应该延续原有 RAG 可观测性设计。

---

## 3\.5 Token 预算信息

```JSON
{
  "maxPromptTokens": 12000,
  "estimatedPromptTokens": 8600,
  "reservedOutputTokens": 3000,
  "systemTokens": 700,
  "memoryTokens": 520,
  "summaryTokens": 900,
  "recentTurnTokens": 3200,
  "ragEvidenceTokens": 3900,
  "currentMessageTokens": 300
}
```

作用：

```Plain Text
让开发者知道 prompt 是不是过长，哪一类上下文占比最高。
```

---

## 3\.6 裁剪信息

```JSON
{
  "truncated": true,
  "truncatedTypes": ["OLDER_RECENT_TURNS", "OPTIONAL_MEMORY"],
  "droppedRecentTurnCount": 2,
  "droppedMemoryCount": 1,
  "droppedEvidenceCount": 0
}
```

作用：

```Plain Text
解释为什么有些历史或记忆没有被使用。
```

这对用户体验也重要。比如用户问：

```Plain Text
你为什么没记得刚才那个细节？
```

可以通过 trace 判断是不是 older recent turns 被裁剪了。

---

## 3\.7 安全与降级信息

```JSON
{
  "fallbackUsed": false,
  "fallbackReason": null,
  "permissionFilteredCount": 0,
  "deletedMemorySkipped": 1,
  "removedKbDocumentSkipped": 0
}
```

如果发生 no\-evidence：

```JSON
{
  "fallbackUsed": true,
  "fallbackReason": "NO_EVIDENCE",
  "modelCallSkipped": true
}
```

作用：

```Plain Text
说明是否因为无证据、权限过滤、检索失败等原因降级。
```

---

# Trace 存在哪里？

我建议有两种选择。

## 方案 A：存在 assistant message 的 metadata 里

如果你有 `conversation_message` 表，可以加：

```Plain Text
metadata_json
```

assistant 消息里存：

```JSON
{
  "contextTrace": {...}
}
```

优点：

```Plain Text
简单
不用新增表
每条 assistant 回复天然对应一个 trace
```

缺点：

```Plain Text
metadata_json 可能越来越大
后续按 trace 字段查询不方便
```

---

## 方案 B：新增 tb\_context\_trace 表

如果你想工程化一点，建议新增：

```Plain Text
tb_context_trace
```

字段：

```Plain Text
id
trace_id
user_id
conversation_id
message_id
context_mode
summary_used
memory_count
recent_turn_count
rag_triggered
knowledge_base_id
evidence_count
estimated_prompt_tokens
truncated_types_json
trace_json
create_time
```

优点：

```Plain Text
结构清晰
方便单独查询
方便统计
方便测试
```

缺点：

```Plain Text
多一张表
实现稍微复杂
```

我的建议：

> 第一版可以先放 message\.metadata\_json；如果你想把它作为亮点，就新增 `tb_context_trace`。
>
>

考虑你这个功能本身就是为了项目包装和工程化，我更推荐新增表。

# Trace 对前端展示什么？

前端不需要展示所有字段。

可以分成“简洁展示”和“调试详情”。

## 简洁展示

在回答下面显示：

```Plain Text
本轮使用：
- 最近 8 轮对话
- 会话摘要
- 3 条长期记忆
- 已触发知识库检索，命中 3 篇文档
```

或者：

```Plain Text
上下文来源：Recent Turns + Summary + Memory + RAG
```

---

## 调试详情

用户点击“查看上下文来源”后展示：

```JSON
{
  "contextMode": "AGENT_MEMORY",
  "summaryUsed": true,
  "memoryCount": 3,
  "recentTurnCount": 8,
  "ragTriggered": true,
  "evidenceCount": 5,
  "estimatedPromptTokens": 8600,
  "truncatedTypes": ["OLDER_RECENT_TURNS"]
}
```

不要展示完整 prompt。

---

# Trace 和 citation 的区别

这两个不要混。

## Citation

回答的是：

```Plain Text
答案依据来自哪篇文档、哪个 chunk？
```

例如：

```Plain Text
[1] ROADMAP_RAG.md chunkIndex=4
```

## Trace

回答的是：

```Plain Text
这次回答整体用了哪些上下文来源？
```

例如：

```Plain Text
用了 3 条 memory、1 个 summary、8 轮 recent turns、5 条 evidence。
```

所以：

```Plain Text
citation 是答案证据
trace 是上下文构建过程
```

---

# Trace 和日志的区别

Trace 不是后端日志。

## 后端日志

给开发者排查异常：

```Plain Text
某个 service 调用失败
某个接口耗时
异常 stack
```

## Context Trace

给用户和开发者解释上下文：

```Plain Text
本轮用了哪些上下文
哪些被裁剪
有没有触发 RAG
```

Trace 必须脱敏，日志也应该脱敏。

---

# Trace 和 eval 的关系

Trace 是单次请求的可观测性。

Eval 是多 case 的质量评估。

比如：

```Plain Text
Trace：这次回答触发 RAG，命中 5 条 evidence。
Eval：100 个测试 case 里 hit@k 是 0.91，citationHitRate 是 0.88。
```

DocPilot RAG 路线里已经有 offline eval 方向，Trace 可以为后续 eval 提供单次请求的证据链。

```Java
public record ContextTrace(

    boolean ragRequired,
    Long knowledgeBaseId,

```

第一版不一定字段这么多，但结构可以按这个方向。

# ContextTraceBuilder 设计

在第 9 节我们设计过：

```Plain Text
ContextTraceBuilder
```

它应该接收：

```Plain Text
ContextAssemblyRequest
List<ContextItem> originalItems
List<ContextItem> usedItems
TokenBudgetResult
RagRetrievalResult
```

然后生成：

```Plain Text
ContextTrace
```

它不负责拼 prompt，不负责查数据，只负责把过程整理成 trace。

---

# Trace 的生命周期

一次消息的完整链路：

```Plain Text
用户发送消息
-> 保存 user message
-> ContextAssemblyService 构建上下文
-> ContextTraceBuilder 生成 preliminary trace
-> AiAnswerService / RAG QA 生成回答
-> 保存 assistant message
-> 保存 contextTrace
-> 返回 answer + contextTrace
```

如果回答失败，也要保存失败 trace：

```Plain Text
fallbackUsed = true
fallbackReason = MODEL_UNAVAILABLE / NO_EVIDENCE / CONTEXT_ASSEMBLY_FAILED
```

这样以后能排查。

---

# Trace 是否给用户关闭？

第一版不需要复杂开关。

可以默认返回简化 trace。

如果担心前端太复杂，可以：

```Plain Text
默认接口返回 contextTraceSummary
调试接口返回 contextTraceDetail
```

例如发送消息接口返回：

```JSON
{
  "answer": "...",
  "contextTraceSummary": {
    "contextMode": "AGENT_MEMORY",
    "summaryUsed": true,
    "memoryCount": 3,
    "ragTriggered": true,
    "evidenceCount": 5
  }
}
```

单独接口返回详细 trace：

```HTTP
GET /api/conversations/{conversationId}/messages/{messageId}/context-trace
```

---

# Trace 失败怎么办？

Trace 失败不能影响回答。

如果 trace 写入失败：

```Plain Text
回答照常返回
日志记录脱敏 warning
traceStatus = FAILED
```

不要因为 trace 落库失败导致用户请求失败。

Trace 是辅助可观测性，不是主业务强依赖。

# 第一版 MVP 建议

第一版做到这些就够：

```Plain Text
1. ContextTrace 对象
2. ContextTraceBuilder
3. 发送消息响应返回 contextTraceSummary
4. 可选：GET message context-trace 详情
5. trace 记录 summaryUsed、memoryCount、recentTurnCount、ragTriggered、evidenceCount、estimatedPromptTokens、truncatedTypes
6. 不记录完整 prompt
7. 不记录完整 memory / summary / evidence
8. trace 写入失败不影响回答
```

暂时不做：

```Plain Text
复杂监控面板
聚合指标 dashboard
OpenTelemetry
链路追踪平台
trace 全文检索
用户自定义 trace 字段
```

# 测试重点

需要测：

```Plain Text
RECENT_TURNS trace：summaryUsed=false，memoryCount=0，ragTriggered=false
AGENT_MEMORY trace：summaryUsed/memoryCount 正确
RAG 触发时 trace 记录 ragTriggered=true、evidenceCount 正确
no-evidence 时 fallbackReason=NO_EVIDENCE
token 超限时 truncatedTypes 正确
trace 不包含完整 prompt
trace 不包含 secret / api key / connection string
用户不能查看别人的 trace
trace 写入失败不影响消息响应
```

# 面试怎么讲？

你可以这样说：

> 我给 Agent Memory Mode 增加了 Context Trace，用来记录每次回答的上下文来源和预算情况。Trace 会记录 contextMode、recentTurnCount、summaryUsed、memoryCount、ragTriggered、evidenceCount、estimatedPromptTokens 和 truncatedTypes，帮助解释模型本轮到底用了哪些上下文。为了隐私安全，Trace 只保存脱敏摘要，不保存完整 prompt、长期记忆原文、RAG evidence 原文、API key、连接串或异常堆栈。Trace 写入失败不会影响主回答，只作为可观测性能力。
>
>

---

# 一句话定方案

我建议 Trace / 可观测性这样定：

> **每次回答都生成一份脱敏 ContextTrace，记录本轮使用了哪些上下文来源、是否触发 RAG、token 预算和裁剪情况；Trace 用于前端解释、调试和面试展示，但不保存完整 prompt、memory、summary、evidence 或任何敏感信息。**
>
>
