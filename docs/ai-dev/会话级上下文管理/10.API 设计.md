# 10\.API 设计

可以，开始 **10\. API 设计**。

这一节要解决的是：

> 前端如何和“会话级上下文管理系统 / Agent Memory Mode”交互？
>
>

前面 1～9 已经定了模式、数据模型、上下文拼接、摘要、长期记忆、RAG 融合、权限、token 预算、ContextAssemblyService。API 设计就是把这些能力暴露给前端。你之前的设计路线里也明确 API 要覆盖：创建会话、发送消息、选择 `contextMode`、保存 memory、查看/删除 memory、绑定 knowledgeBase、查看当前会话使用了哪些上下文。

---

# 1\. API 设计总原则

我建议遵守 5 个原则：

```Plain Text
1. 前端不传 userId，后端统一从 UserHolder.requireUserId() 获取
2. contextMode 在创建会话时确定，默认 RECENT_TURNS
3. AGENT_MEMORY 会话可以绑定 knowledgeBaseId
4. 发送消息接口只负责发消息，不让前端手动拼 context
5. 返回 answer 时附带 contextTrace，但不返回完整 prompt
```

也就是说，前端只告诉后端：

```Plain Text
我在哪个会话里发了什么消息
```

后端负责：

```Plain Text
读取 conversation
判断 contextMode
调用 ContextAssemblyService
拼接上下文
调用模型 / RAG
返回回答和 trace
```

前端不应该参与 prompt 拼接。

# 2\. Conversation API

## 2\.1 创建会话

```HTTP
POST /api/conversations
```

请求：

```JSON
{
  "title": "DocPilot 项目助手",
  "contextMode": "AGENT_MEMORY",
  "boundKnowledgeBaseId": 12
}
```

说明：

```Plain Text
title 可选
contextMode 可选，默认 RECENT_TURNS
boundKnowledgeBaseId 可选，只在 AGENT_MEMORY 下有意义
```

后端逻辑：

```Plain Text
1. currentUserId = UserHolder.requireUserId()
2. 校验 contextMode 合法
3. 如果传了 boundKnowledgeBaseId，校验 KB 属于当前用户
4. 创建 conversation
```

响应：

```JSON
{
  "conversationId": 1001,
  "title": "DocPilot 项目助手",
  "contextMode": "AGENT_MEMORY",
  "boundKnowledgeBaseId": 12,
  "createdAt": "2026-06-11T10:00:00"
}
```

---

## 2\.2 获取会话列表

```HTTP
GET /api/conversations
```

响应：

```JSON
{
  "items": [
    {
      "conversationId": 1001,
      "title": "DocPilot 项目助手",
      "contextMode": "AGENT_MEMORY",
      "boundKnowledgeBaseId": 12,
      "lastMessagePreview": "我们继续设计 API...",
      "updatedAt": "2026-06-11T10:00:00"
    }
  ]
}
```

只返回当前用户自己的会话。

---

## 2\.3 获取会话详情

```HTTP
GET /api/conversations/{conversationId}
```

响应：

```JSON
{
  "conversationId": 1001,
  "title": "DocPilot 项目助手",
  "contextMode": "AGENT_MEMORY",
  "boundKnowledgeBaseId": 12,
  "summaryEnabled": true,
  "memoryEnabled": true,
  "ragTriggerMode": "AUTO",
  "createdAt": "2026-06-11T10:00:00",
  "updatedAt": "2026-06-11T10:00:00"
}
```

后端必须校验：

```Plain Text
conversation.userId == currentUserId
```

# 3\. 发送消息 API

这是核心接口。

```HTTP
POST /api/conversations/{conversationId}/messages
```

请求：

```JSON
{
  "content": "请结合当前知识库，帮我总结这个系统的 API 设计。"
}
```

不要让前端传：

```Plain Text
userId
memory
summary
recentTurns
ragEvidence
prompt
```

这些都由后端构建。

后端流程：

```Plain Text
1. 校验 conversation 属于 currentUserId
2. 保存 user message
3. 调用 ContextAssemblyService.buildContext()
4. 根据 contextMode 组装 prompt
5. 如果需要 RAG，调用 KnowledgeBaseRagRetrievalService
6. 调用 AiAnswerService 生成回答
7. 保存 assistant message
8. maybeScheduleSummary()
9. 返回 answer + citations + contextTrace
```

响应：

```JSON
{
  "messageId": 9002,
  "conversationId": 1001,
  "role": "assistant",
  "content": "这套 API 可以分为会话、消息、记忆、知识库绑定和上下文 Trace 五类...",
  "citations": [
    {
      "index": 1,
      "knowledgeBaseId": 12,
      "documentId": 83,
      "documentTitle": "ROADMAP_RAG.md",
      "chunkIndex": 4,
      "score": 0.82,
      "snippet": "..."
    }
  ],
  "contextTrace": {
    "contextMode": "AGENT_MEMORY",
    "summaryUsed": true,
    "memoryCount": 3,
    "recentTurnCount": 8,
    "ragTriggered": true,
    "ragRequired": true,
    "knowledgeBaseId": 12,
    "evidenceCount": 5,
    "estimatedPromptTokens": 8600,
    "truncatedTypes": ["OLDER_RECENT_TURNS"]
  }
}
```

注意：

```Plain Text
contextTrace 不返回完整 prompt
citations 可返回安全 snippet
```

DocPilot 原 RAG 主线本身已经包含 prompt 上下文构造、LLM 回答、citation、Agent Trace / eval 记录这些环节，所以这个消息 API 可以延续已有 RAG / Trace 结构。

# 5\. ContextMode API

我建议第一版不要做“随时切换模式”。

创建时确定：

```Plain Text
RECENT_TURNS
AGENT_MEMORY
```

但可以支持从标准模式升级到 Agent Memory Mode。

## 5\.1 升级会话模式

```HTTP
PATCH /api/conversations/{conversationId}/context-mode
```

请求：

```JSON
{
  "contextMode": "AGENT_MEMORY"
}
```

后端规则：

```Plain Text
RECENT_TURNS -> AGENT_MEMORY 允许
AGENT_MEMORY -> RECENT_TURNS 第一版不建议允许
```

如果要降级，建议前端提示：

```Plain Text
如需干净上下文，请新建标准会话。
```

响应：

```JSON
{
  "conversationId": 1001,
  "contextMode": "AGENT_MEMORY",
  "summaryEnabled": true,
  "memoryEnabled": true
}
```

# 6\. Memory API

长期记忆要独立 API。

## 6\.1 保存 memory

```HTTP
POST /api/memories
```

请求：

```JSON
{
  "memoryType": "PREFERENCE",
  "content": "用户希望回答先给结论，再解释工程取舍。"
}
```

后端逻辑：

```Plain Text
1. currentUserId = UserHolder.requireUserId()
2. MemorySafetyValidator 检查是否包含 key/token/password 等敏感信息
3. 保存为 ACTIVE memory
```

响应：

```JSON
{
  "memoryId": 501,
  "memoryType": "PREFERENCE",
  "content": "用户希望回答先给结论，再解释工程取舍。",
  "status": "ACTIVE",
  "createdAt": "2026-06-11T10:00:00"
}
```

---

## 6\.2 查看 memory 列表

```HTTP
GET /api/memories
```

可按类型过滤：

```HTTP
GET /api/memories?memoryType=PROJECT_STATE
```

响应：

```JSON
{
  "items": [
    {
      "memoryId": 501,
      "memoryType": "PREFERENCE",
      "content": "用户希望回答先给结论，再解释工程取舍。",
      "status": "ACTIVE",
      "priority": 80,
      "updatedAt": "2026-06-11T10:00:00"
    }
  ]
}
```

只返回当前用户自己的 memory。

---

## 6\.3 修改 memory

```HTTP
PATCH /api/memories/{memoryId}
```

请求：

```JSON
{
  "content": "用户希望回答先给结论，再分点解释。",
  "priority": 90,
  "status": "ACTIVE"
}
```

后端必须：

```Plain Text
where id = ? and user_id = currentUserId
```

---

## 6\.4 删除 memory

```HTTP
DELETE /api/memories/{memoryId}
```

软删除：

```Plain Text
ACTIVE -> DELETED
```

响应：

```JSON
{
  "memoryId": 501,
  "status": "DELETED"
}
```

硬规则：

```Plain Text
DELETED memory 不再注入 prompt
```

# 7\. Conversation Summary API

摘要可以给用户查看，但第一版不一定允许编辑。

## 7\.1 查看当前会话摘要

```HTTP
GET /api/conversations/{conversationId}/summary
```

响应：

```JSON
{
  "conversationId": 1001,
  "summary": "本会话主要讨论 DocPilot 会话级上下文管理系统，已确定...",

```

如果没有摘要：

```JSON

  "conversationId": 1001,

  "status": "NOT_FOUND"

```

---

## 7\.2 删除摘要

```HTTP
DELETE /api/conversations/{conversationId}/summary
```

响应：

```JSON
{
  "conversationId": 1001,
  "status": "DELETED"
}
```

删除后：

```Plain Text
summary 不再注入 prompt

```


# 8\. 知识库绑定 API

## 8\.1 绑定知识库

```HTTP
PATCH /api/conversations/{conversationId}/knowledge-base
```

请求：

```JSON
{
  "knowledgeBaseId": 12
}
```

后端逻辑：

```Plain Text
1. 校验 conversation 属于 currentUserId
2. 校验 knowledgeBase 属于 currentUserId
3. 更新 boundKnowledgeBaseId
```

你的 T011 设计里已经有 `KnowledgeBaseScopeGuard`，用于校验 KB owner、文档归属、ACTIVE 成员文档。这里应该复用它，不要重新写一套权限逻辑。

响应：

```JSON
{
  "conversationId": 1001,
  "boundKnowledgeBaseId": 12
}
```

---

## 8\.2 解除绑定

```HTTP
DELETE /api/conversations/{conversationId}/knowledge-base
```

响应：

```JSON
{
  "conversationId": 1001,
  "boundKnowledgeBaseId": null
}
```

# 9\. Context Trace API

发送消息时已经可以返回 `contextTrace`。

但也可以提供单独查看某条消息 trace 的接口：

```HTTP
GET /api/conversations/{conversationId}/messages/{messageId}/context-trace
```

响应：

```JSON
{
  "messageId": 9002,
  "contextMode": "AGENT_MEMORY",
  "summaryUsed": true,
  "memoryCount": 3,
  "recentTurnCount": 8,
  "ragTriggered": true,
  "knowledgeBaseId": 12,
  "evidenceCount": 5,
  "estimatedPromptTokens": 8600,
  "truncatedTypes": ["OLDER_RECENT_TURNS"]
}
```

不要返回：

```Plain Text
完整 prompt
完整 memory 内容
完整 summary 内容
完整 evidence 原文
API key
连接串
异常堆栈
```

DocPilot 的环境边界本身也强调不要暴露 `.env`、API key、SSH 信息、数据库密码、真实 token、服务器 IP，本地单元测试也不应该强依赖远程服务器。

# 11\. API 分组建议

推荐 Controller 分组：

```Plain Text
ConversationController
- 创建会话
- 会话列表
- 会话详情
- 修改 contextMode
- 绑定 / 解绑 knowledgeBase

ConversationMessageController
- 发送消息
- 查看消息历史
- 查看消息 contextTrace

UserMemoryController
- 保存 memory
- 查看 memory
- 修改 memory
- 删除 memory

ConversationSummaryController
- 查看 summary
- 删除 summary
- 重新生成 summary，可选
```

不要把所有接口都塞进一个 Controller。

# 13\. 错误码设计

建议新增或复用这些错误码：

```Plain Text
CONVERSATION_NOT_FOUND
CONVERSATION_FORBIDDEN
INVALID_CONTEXT_MODE
MEMORY_NOT_FOUND
MEMORY_FORBIDDEN
MEMORY_SENSITIVE_CONTENT_REJECTED
SUMMARY_NOT_FOUND
KNOWLEDGE_BASE_NOT_FOUND
KNOWLEDGE_BASE_FORBIDDEN
CONTEXT_ASSEMBLY_FAILED
```

注意区分：

```Plain Text
NOT_FOUND：资源不存在
FORBIDDEN：资源存在但不属于当前用户
```

对外可以统一模糊化：

```Plain Text
资源不存在或无权限访问
```

避免暴露资源是否真实存在。

我建议发送消息响应一定要有：

```JSON
{
  "conversationId": 1001,
  "messageId": 9002,
  "answer": "...",
  "contextMode": "AGENT_MEMORY",
  "citations": [],

    "summaryUsed": true,

    "recentTurnCount": 8,
    "ragTriggered": false,
    "evidenceCount": 0,
    "estimatedPromptTokens": 5200,
    "truncatedTypes": []
  }

```

这样前端可以显示：

```Plain Text

```

这对产品体验和面试展示都有价值。

# 15\. 权限规则再次强调

所有 API 都必须：

```Plain Text
不接收 body.userId
只从 UserHolder 获取 currentUserId
所有资源查找都带 userId
所有绑定操作都做 owner 校验
所有 deleted / removed 状态不参与 prompt 注入
```

尤其是：

```Plain Text
memory
summary
knowledgeBase
conversation
```

这几个一旦越权，就是严重隐私问题。

# 16\. 面试怎么讲？

你可以这样讲：

> API 层我按资源拆成 Conversation、Message、Memory、Summary 和 KnowledgeBase Binding。前端创建会话时选择 contextMode，默认 RECENT\_TURNS，也可以选择 AGENT\_MEMORY 并绑定知识库。发送消息时前端只提交 content，不传 userId、summary、memory 或 prompt，后端通过 ContextAssemblyService 根据会话模式统一构建上下文。长期记忆支持用户显式保存、查看和删除；知识库绑定时复用 KnowledgeBaseScopeGuard 校验 owner。每次回答返回 contextTrace，展示 memoryCount、summaryUsed、ragTriggered、evidenceCount 和 token 估算，但不返回完整 prompt 和敏感信息。
>
>

---

# 17\. 一句话定方案

我建议 API 设计这样定：

> **API 按会话、消息、长期记忆、会话摘要和知识库绑定拆分；创建会话时确定 contextMode，发送消息时只传 content，后端通过 ContextAssemblyService 统一拼接上下文；memory、summary、knowledgeBase 都必须做 owner 校验；响应返回 answer、citations 和脱敏 contextTrace，不暴露完整 prompt。**
>
>
