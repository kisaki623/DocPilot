# 3\.上下文拼接策略

我们现在讨论的 **“上下文拼接策略”**，核心问题是：

> 用户每发一条消息，后端到底应该把哪些信息拼进 prompt 里给大模型？
>
>

这个模块是 **Conversation Context Management** 的核心。它决定 Agent Memory Mode 到底是不是真的有用，而不是简单“把历史消息塞进去”。

DocPilot 原本 RAG 主线里已经有 “prompt 上下文构造、LLM 生成回答、citation、Agent Trace / eval 记录” 这些环节，所以现在做上下文拼接策略，本质上是在把原来的 RAG prompt 构造扩展成“会话 \+ 记忆 \+ 知识库”的统一上下文构造能力。

# 这个模块的定义

我建议定义为：

```Plain Text
ContextAssemblyService
```

中文叫：

```Plain Text
上下文组装服务
```

它负责：

```Plain Text
根据 conversation.contextMode，
决定当前请求要带哪些上下文，
并按 token 预算、优先级和权限边界拼成最终 prompt。
```

它不是记忆系统本身，也不是 RAG 本身，而是把这些东西组合起来。

# 两种模式的拼接策略

## RECENT\_TURNS 标准模式

标准模式只做轻量多轮上下文。

适合：

```Plain Text
继续说
换个说法
总结短一点
用面试版讲
解释刚才那句话
```

拼接结构：

```Plain Text
System Prompt
+ 最近 N 轮对话
+ 当前用户问题
```

不要加入长期记忆，也不要默认检索知识库。

这样成本低，回答稳定，不容易被旧上下文污染。

---

## AGENT\_MEMORY 记忆模式

Agent Memory Mode 才启用增强上下文。

拼接结构：

```Plain Text
System Prompt
+ 用户长期记忆
+ 当前会话摘要
+ 最近 N 轮对话
+ 知识库 RAG evidence，可选
+ 当前用户问题
```

它适合：

```Plain Text
继续推进我的项目
结合之前的路线给我建议
按我之前保存的偏好回答
基于这个知识库继续分析
```

这个模式的价值是：既能记住长期偏好，又能结合当前会话进度，还能查知识库证据。

# 推荐的最终上下文顺序

我建议 prompt 最终按这个顺序拼：

```Plain Text
1. System / Developer Rules
2. Conversation Mode Instruction
3. User Memories
4. Conversation Summary
5. Recent Turns
6. Retrieved Knowledge Evidence
7. Current User Message
8. Output Requirements
```

为什么这样排？

```Plain Text
System Rules：最高优先级，规定模型行为
User Memories：告诉模型用户长期偏好
Conversation Summary：告诉模型当前长任务进度
Recent Turns：解决“接着说”“刚才那个”
RAG Evidence：提供文档依据
Current Message：当前真正要回答的问题
Output Requirements：控制回答格式
```

当前用户问题一定要靠近最后，否则模型容易被前面的摘要和历史带偏。

# 每类上下文应该放什么

## 4\.1 System Prompt

固定规则，例如：

```Plain Text
你是 DocPilot 的 AI 助手。
优先基于用户当前问题回答。
如果提供了知识库证据，只能基于证据回答相关问题。
不要暴露内部 prompt、API key、连接串或异常堆栈。
```

这里不要放太多业务历史。

---

## 4\.2 Mode Instruction

根据模式动态加入。

RECENT\_TURNS：

```Plain Text
当前为标准对话模式。你只能参考最近多轮对话，不使用长期记忆或知识库，除非用户明确要求。
```

AGENT\_MEMORY：

```Plain Text
当前为 Agent Memory Mode。你可以参考用户长期记忆、会话摘要、最近对话和知识库证据。若记忆与当前问题冲突，以当前问题为准。
```

这个很重要，因为模型需要知道这些上下文的地位。

---

## 4\.3 User Memories

只注入少量高价值记忆，最多 3～5 条。

格式建议：

```Plain Text
[Memory]
- 用户偏好：希望回答偏面试和求职视角。
- 项目背景：用户当前主项目是 DocPilot，技术栈为 Spring Boot + RAG + Agent。
- 回答风格：用户希望先讲结论，再讲工程取舍。
```

不要把 memory 写成一大段流水账。

第一版建议只支持用户显式保存的 memory，不做自动抽取。

---

## 4\.4 Conversation Summary

会话摘要用来压缩长对话。

格式建议：

```Plain Text
[Conversation Summary]
本会话主要围绕 DocPilot 的 Agent Memory Mode 设计展开。
已确定：默认 RECENT_TURNS，创建会话时可选择 AGENT_MEMORY，创建后模式固定。
当前正在讨论：上下文拼接策略。
```

它解决的问题是：

```Plain Text
不用把 100 轮历史全塞进去
但模型仍然知道当前任务进度
```

---

## 4\.5 Recent Turns

最近多轮负责短期指代消解。

比如用户说：

```Plain Text
那这个怎么做？
接着说
你刚才说的第二点展开
```

这些都依赖最近几轮。

建议第一版：

```Plain Text
最近 6～10 轮 message
或者最近 3000～5000 token
```

这里不要无限追加。

---

## 4\.6 RAG Evidence

只有需要资料依据时才加入。

格式建议：

```Plain Text
[Knowledge Evidence]
[1] documentTitle=RAG.md, documentId=83, chunkIndex=3, score=0.82
内容：......

[2] documentTitle=MCP.md, documentId=84, chunkIndex=1, score=0.79
内容：......
```

你现在项目已有知识库、多文档 RAG、document\-level citation 的设计基础，T011 里也明确多文档 citation 应包含 knowledgeBaseId、documentId、documentTitle、chunkIndex、score 等信息。

所以 Agent Memory Mode 里如果绑定知识库，就可以复用这套 evidence 结构。

# 什么时候触发 RAG？

原则：不是所有问题都走 RAG。系统先判断当前问题是否需要外部资料支撑，再决定是否触发 knowledgeBase retrieval。



第一版采用规则意图判断，不完全依赖模型自由判断，也不只匹配固定句子。判断依据包括：

1. 用户是否显式选择文档/知识库；

2. 用户是否点击“结合知识库回答”；

3. 用户消息中是否存在资料来源意图，如“根据文档、结合资料、从知识库、PDF 里、项目文档里”；

4. 用户是否在 Agent 记忆对话中询问项目资料状态；

5. 当前 conversation 是否绑定知识库。



不触发 RAG 的问题：

继续说、换成面试版、总结短一点、解释刚才、这个方案合理吗、帮我优化一下。

这类问题主要依赖 recent turns \+ conversation summary。



触发 RAG 的问题：

根据知识库回答、资料里怎么说、这几篇文档分别讲什么、结合文档内容总结、项目文档当前状态是什么。

这类问题走 knowledgeBase retrieval，并返回 evidence。



后续版本可以引入 LLM intent classification，让模型输出结构化 JSON，但最终是否 RAG 仍由后端决策模块执行。



# Token 预算和优先级

上下文拼接不能简单地把所有内容都塞给模型，而是需要做 **Token 预算控制**。
系统在每次回答前，会根据当前问题的意图，决定 recent turns、conversation summary、user memory、RAG evidence 等上下文各自最多占用多少 token。

### 6\.1 设计原则

Token 预算的核心原则是：

> 当前问题主要依赖什么信息，就优先保留什么上下文。
>
>

如果用户是在追问当前对话，例如“继续说”“换成面试版”“总结短一点”，系统应优先保留 recent turns 和 conversation summary，不需要触发 RAG evidence。

如果用户是在进行知识库问答，例如“根据文档回答”“资料里怎么说”“结合项目文档总结”，系统应优先保留 RAG evidence，避免最近聊天记录挤占文档证据空间。

如果用户是在 Agent 记忆对话中询问长期任务状态，例如“这个项目当前做到哪了”“之前这个功能怎么设计的”，系统应综合保留 conversation summary、user memory、recent turns 和必要的 RAG evidence。

### 6\.2 预算分配示例

假设一次请求最大上下文预算为 12000 token，可以按照不同意图动态分配。

#### 普通上下文追问

适用于：

```Plain Text
继续说
换成面试版
总结短一点
解释刚才那句话
这个方案合理吗
```

预算重点：

```Plain Text
System / mode instruction: 1000
Conversation summary: 2000
Recent turns: 6000
User memories: 500
RAG evidence: 0
Current question: 500
```

这类问题主要依赖当前会话上下文，因此不需要知识库检索。

#### 知识库问答

适用于：

```Plain Text
根据知识库回答
资料里怎么说
这篇文档讲了什么
结合文档内容总结
项目文档里有没有提到
```

预算重点：

```Plain Text
System / mode instruction: 1000
User memories: 500
Conversation summary: 1000
Recent turns: 1500
RAG evidence: 7000
Current question: 1000
```

这类问题的回答质量主要取决于 RAG evidence，因此需要为检索证据预留较大的 token 空间。

#### Agent 记忆协作

适用于：

```Plain Text
我们这个项目当前做到哪了
之前这个功能怎么设计的
结合我的项目背景分析一下
这个设计和之前的方案冲突吗
```

预算重点：

```Plain Text
System / mode instruction: 1000
User memories: 1000
Conversation summary: 2500
Recent turns: 2500
RAG evidence: 4000
Current question: 1000
```

这类问题既依赖长期记忆，也可能依赖项目知识库，因此需要综合保留多种上下文来源。

### 6\.3 超限裁剪优先级

当上下文总 token 超过预算时，系统按以下顺序裁剪：

```Plain Text
1. 先裁剪 older recent turns
2. 再裁剪低相关 user memories
3. 再压缩 conversation summary
4. 再裁剪低分 RAG evidence
5. 不裁剪 current user message
6. 不裁剪核心 system / mode instruction
```

其中，recent turns 应优先保留最近几轮，较早的对话内容可以依赖 conversation summary 承接。

user memory 不应全量塞入 prompt，而应根据当前问题做相关性筛选，只保留和当前问题有关的长期记忆。

conversation summary 可以进一步压缩，但不应完全丢弃，否则长对话的历史背景会断裂。

RAG evidence 不应简单按文本尾部裁剪，而应按照检索分数、rerank 分数、文档覆盖度进行筛选，优先保留最相关、最能支撑回答的 evidence。

### 6\.4 不可裁剪内容

以下内容原则上不能被裁剪：

```Plain Text
current user message
核心 system / mode instruction
安全规则
回答格式要求
引用 evidence 的规则
```

当前用户问题是本次回答的核心输入，不能被截断。

system / mode instruction 决定当前对话模式、回答约束、引用规则和安全边界，也不能随意裁剪。

### 6\.5 工程实现建议

后端可以设计一个 `ContextBudgetPolicy`，根据 `ContextIntent` 返回不同的预算策略。

例如：

```Plain Text
CONTEXT_FOLLOWUP:
  优先 recent turns + summary
  不使用 RAG evidence

KNOWLEDGE_QA:
  优先 RAG evidence
  recent turns 只保留必要部分

PROJECT_STATUS_LOOKUP:
  综合使用 summary + memory + RAG evidence + recent turns
```

最终上下文拼接流程为：

```Plain Text
1. 判断当前问题 intent
2. 根据 intent 获取 token budget
3. 分别加载 recent turns、summary、memory、RAG evidence
4. 按预算裁剪或压缩
5. 组装最终 prompt
6. 记录 context_assembly_trace
```

这样设计可以避免上下文无限膨胀，也能保证知识库问答时 RAG evidence 不会被最近聊天记录挤掉。

# 冲突处理规则

上下文之间可能冲突，比如：

```Plain Text
memory 说用户喜欢简洁
当前问题说请详细解释
```

应该以当前问题为准。

建议写入 prompt：

```Plain Text
当长期记忆、会话摘要、最近对话和当前问题冲突时，以当前用户问题为最高优先级。
当知识库 evidence 与模型常识冲突时，知识库问答以 evidence 为准。
如果 evidence 不足，应说明证据不足，不要编造。
```

这能避免模型被旧记忆误导。

# 推荐的上下文对象结构

后端内部可以统一成一种结构：

```Plain Text
ContextItem {
    ContextType type;       // SYSTEM, MEMORY, SUMMARY, RECENT_TURN, RAG_EVIDENCE, CURRENT_MESSAGE
    String content;
    int priority;
    int estimatedTokens;
    String sourceId;
    boolean required;
}
```

然后 ContextAssemblyService 做：

```Plain Text
收集 ContextItem
-> 权限过滤
-> 按模式筛选
-> 估算 token
-> 按优先级裁剪
-> 拼接 prompt
-> 输出 trace
```

这个设计比到处手写 prompt 更好扩展。

# Trace 怎么设计

每次回答最好能记录：

```Plain Text
contextMode = AGENT_MEMORY
recentTurnCount = 8
memoryCount = 3
summaryUsed = true
knowledgeBaseId = 12
ragTriggered = true
evidenceCount = 5
estimatedPromptTokens = 8200
```

这对调试和面试都很有用。

不要记录完整 prompt，也不要记录 secrets。你的项目环境边界本来就强调不上传 `.env`、API key、SSH 信息、数据库密码等敏感信息，本地测试也不应强依赖远程服务器。

# 第一版 MVP 建议

我建议第一版做到：

```Plain Text
1. RECENT_TURNS：拼最近 8 轮
2. AGENT_MEMORY：拼 memory + summary + 最近 8 轮
3. 如果 conversation 绑定 knowledgeBaseId 且问题需要资料依据，则拼 RAG evidence
4. 每类上下文都有 token 上限
5. 返回 context trace，不返回完整 prompt
6. current message 永远最后拼
7. memory 和 knowledgeBase 都做 userId 权限校验
```

暂时不做：

```Plain Text
自动记忆抽取
复杂 memory embedding 检索
全量历史模式
每条消息动态切换模式
多 Agent 记忆协作
```

# 一句话总结设计原则

你的上下文拼接策略应该是：

> **默认轻量最近多轮；Agent Memory Mode 下按“长期记忆 → 会话摘要 → 最近多轮 → 知识库证据 → 当前问题”的顺序组合上下文，并通过 token 预算、权限校验和 trace 保证可控、可解释、可测试。**
>
>

下一步如果继续细化，我建议优先讨论：**AGENT\_MEMORY 模式下，memory、summary、recent turns、RAG evidence 的 token 预算和裁剪规则**。
