# 4\.会话摘要机制设计

我们现在讨论的 **4\. 会话摘要机制**，我建议先把它定义清楚：

> **会话摘要不是长期记忆，也不是知识库 RAG，而是“当前会话的压缩版上下文”。**
>
>

它解决的是：长对话不能一直把所有历史消息塞进 prompt，但又不能完全丢掉前面讨论过的任务进度。你前面整理的模块里也把“会话摘要机制”定位为解决“长对话不能全塞 prompt”的问题，包括什么时候生成、覆盖哪些消息、如何更新、是否可查看、失败怎么办、和最近多轮如何组合。

# 先给会话摘要机制定性

我建议叫：

```Plain Text
Conversation Summary / Rolling Summary
```

中文叫：

```Plain Text
会话滚动摘要
```

它的作用是：

```Plain Text
把较早的多轮消息压缩成一段结构化摘要，
然后和最近几轮原始消息一起拼进 prompt。
```

它不是：

```Plain Text
不是用户长期记忆
不是知识库资料
不是全量历史
不是用户偏好库
```

它只属于当前 conversation。

# 什么时候生成摘要？

我建议第一版只在 **AGENT\_MEMORY 模式**下生成摘要。

标准模式 RECENT\_TURNS 默认不生成摘要，只保留最近几轮即可。

触发条件可以设计成两个：

```Plain Text
1. 未摘要消息数量达到阈值，比如 8～12 条
2. 未摘要消息 token 数达到阈值，比如 3000～5000 token
```

满足任意一个就触发摘要。

推荐规则：

```Plain Text
当 conversation.contextMode = AGENT_MEMORY
并且 unsummarizedTokenCount >= 4000
或者 unsummarizedMessageCount >= 10
则在本轮 assistant 回复完成后异步生成摘要。
```

注意：**不要在用户等待回答时同步生成摘要**。
 否则用户发一条消息，系统先总结一遍，再回答，延迟会明显上升。

更好的流程是：

```Plain Text
用户提问
-> 正常回答
-> 保存 user/assistant message
-> 判断是否需要摘要
-> 异步生成 / 更新 summary
```

# 摘要覆盖哪些消息？

不要把最近几轮也摘要掉。

因为最近几轮最适合处理：

```Plain Text
接着说
这个呢
刚才第二点展开
换成面试版
```

所以摘要应该覆盖“较早的消息”，最近几轮保留原文。

建议：

```Plain Text
summary 覆盖从 conversation 开始到某个 messageId 的旧消息
recent turns 保留最后 6～10 轮原始消息
```

举例：

```Plain Text
消息 1～30：已经压缩成 summary
消息 31～40：作为 recent turns 原文保留
当前消息 41：本轮用户问题
```

拼 prompt 时：

```Plain Text
summary(1～30)
+ recent turns(31～40)
+ current message(41)
```

这样既省 token，又保留近期细节。

# 摘要如何更新？

我建议用 **滚动摘要**，不要每次从头总结全部历史。

更新方式：

```Plain Text
旧 summary
+ 新增未摘要消息
-> 新 summary
```

也就是：

```Plain Text
summary_v1 覆盖 message 1～20
新消息 21～30 达到阈值
-> 用 summary_v1 + message 21～30 生成 summary_v2
-> summary_v2 覆盖 message 1～30
```

这样成本低，而且不会反复处理全部历史。

数据库里需要记录：

```Plain Text
covered_start_message_id
covered_end_message_id
summary_version
status
```

这样你知道当前 summary 覆盖到了哪里。

# 摘要应该长什么样？

不要让模型生成一段散文式摘要。

建议生成结构化摘要，方便后续注入 prompt。

格式可以是：

```Plain Text
[Conversation Summary]
- 当前主题：DocPilot 会话级上下文管理系统设计。
- 已确定决策：
  1. 会话模式分为 RECENT_TURNS 和 AGENT_MEMORY。
  2. 创建会话时选择模式，创建后默认固定。
  3. Agent Memory Mode 会组合最近多轮、会话摘要、长期记忆和知识库 RAG evidence。
- 当前进度：正在设计第 4 部分：会话摘要机制。
- 用户偏好：希望先给工程设计结论，再拆实现细节。
- 待讨论问题：摘要生成时机、覆盖范围、更新策略、失败处理、与最近多轮组合方式。
```

这里要注意：

```Plain Text
用户偏好如果只是本会话临时表现，可以放 summary；
如果用户明确要求长期记住，再进 user_memory。
```

不要把 summary 和长期记忆混在一起。

# 摘要是否可查看？

我建议可以查看，但第一版不一定允许编辑。

可以在前端会话设置里展示：

```Plain Text
当前会话摘要
覆盖消息：1～30
更新时间：2026-xx-xx
状态：ACTIVE
```

用户可以：

```Plain Text
查看摘要
删除摘要
手动重新生成摘要
```

第一版不建议让用户直接编辑摘要，因为编辑后会带来：

```Plain Text
用户修改内容是否可信？
是否会污染 prompt？
是否要记录版本？
```

所以第一版先做“查看 \+ 删除 \+ 重新生成”即可。

# 摘要失败怎么办？

摘要失败不能影响正常聊天。

失败时：

```Plain Text
本轮回答照常返回
summary status = FAILED
记录失败原因的安全摘要
下次达到条件时可以重试
```

Prompt 拼接时如果 summary 不可用，就降级为：

```Plain Text
最近多轮消息 + 当前问题
```

不要因为摘要失败让整个 Agent Memory Mode 不可用。

错误信息也不要暴露：

```Plain Text
API key
连接串
完整异常堆栈
内部服务器地址
```

你的项目环境边界本来就强调不上传 `.env`、API key、SSH 信息、数据库密码等敏感信息，本地测试也不应该强依赖远程服务器。

# 摘要和最近多轮如何组合？

这是核心。

我建议规则是：

```Plain Text
summary 负责长期任务进度
recent turns 负责短期指代和细节
```

拼接顺序：

```Plain Text
System Prompt
+ Mode Instruction
+ User Memories，可选
+ Conversation Summary
+ Recent Turns
+ RAG Evidence，可选
+ Current User Message
```

其中：

```Plain Text
summary 放在 recent turns 前面
current user message 永远放最后
```

这样模型先知道大背景，再看最近对话，最后处理当前问题。

# 数据表设计建议

可以设计一张表：

```Plain Text
tb_conversation_summary
```

字段：

```Plain Text
id
conversation_id
user_id
summary
covered_start_message_id
covered_end_message_id
summary_version
status          // ACTIVE / GENERATING / FAILED / DELETED
token_count
model_provider
model_name
error_type
error_message
create_time
update_time
```

几个关键点：

```Plain Text
user_id 用于权限隔离
covered_end_message_id 用于判断哪些消息已经被摘要
summary_version 用于滚动更新
status 用于失败降级
token_count 用于 token 预算
```

# 服务设计建议

核心服务可以这样拆：

```Plain Text
ConversationSummaryService
- maybeScheduleSummary(conversationId)
- generateSummary(conversationId)
- getActiveSummary(conversationId)
- deleteSummary(conversationId)
- regenerateSummary(conversationId)
```

上下文拼接时由：

```Plain Text
ContextAssemblyService
```

调用：

```Plain Text
ConversationSummaryService.getActiveSummary()
```

不要让每个 QA / Agent / RAG 服务自己查 summary。

# 第一版 MVP 我建议做到什么程度？

第一版做这些就够：

```Plain Text
1. 只在 AGENT_MEMORY 模式启用 summary
2. 最近 8 轮消息永远保留原文
3. 超过 10 条未摘要消息或 4000 token 后触发摘要
4. 摘要异步生成，不阻塞用户回答
5. 摘要使用 rolling summary：旧 summary + 新消息 -> 新 summary
6. summary 存 covered_start/end_message_id
7. summary 失败时降级到 recent turns
8. prompt 中 summary 放在 recent turns 前面
9. 用户可以查看和删除 summary
```

暂时不做：

```Plain Text
用户编辑摘要
多版本摘要对比
自动从摘要抽取长期记忆
summary embedding 检索
跨会话 summary 共享
```

# 测试重点

需要测这些：

```Plain Text
RECENT_TURNS 模式不会生成 summary
AGENT_MEMORY 模式达到阈值后生成 summary
summary 覆盖旧消息，不覆盖最近 N 轮
rolling summary 更新 covered_end_message_id
summary 失败不影响正常回答
summary DELETED 后不再注入 prompt
不同用户不能读取别人的 summary
ContextAssemblyService 能正确组合 summary + recent turns
```

# 面试怎么讲？

你可以这样说：

> 我没有把全量历史都塞进 prompt，而是设计了会话滚动摘要机制。Agent Memory Mode 下，系统会保留最近几轮原始消息用于短期指代，把更早的消息压缩成 conversation summary。摘要采用 rolling summary 更新方式，即旧摘要加新增未摘要消息生成新摘要，并记录 covered\_message\_id 范围。摘要生成放在回答完成后的异步流程里，失败时不会影响正常对话，只是降级为最近多轮上下文。这样既控制 token 成本，又能保留长任务的阶段性决策和当前进度。
>
>

# 一句话定方案

我建议会话摘要机制这样定：

> **Agent Memory Mode 下启用会话滚动摘要：保留最近 6～10 轮原始消息，较早消息压缩成结构化 summary；summary 异步生成、滚动更新、可查看可删除，失败时降级到最近多轮，不阻塞正常回答。**
>
>
