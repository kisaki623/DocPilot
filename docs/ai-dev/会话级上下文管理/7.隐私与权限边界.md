# 7\.隐私与权限边界

我们现在讨论 **7\. 隐私与权限边界**。这一节是整个 **会话级上下文管理系统 / Agent Memory Mode** 里最容易被面试官追问的部分。

它要解决的问题是：

> **Agent Memory Mode 会读取会话、摘要、长期记忆、知识库、RAG evidence，如果权限边界没做好，就可能出现跨用户记忆泄露、知识库越权、deleted memory 继续注入 prompt、trace 暴露敏感信息等问题。**
>
>

你前面的系统设计里也明确把这一节定位为：用户只能访问自己的 conversation、memory、knowledgeBase，敏感信息不默认保存，memory 可查看/删除，deleted memory 不再注入 prompt。
 同时 DocPilot 环境边界里已经强调不能上传 `.env`、API key、SSH 信息、数据库密码、真实 token，也不能公开真实服务器 IP。



# 这一节的核心原则

我建议把隐私与权限边界定成 6 条原则：

```Plain Text
1. 所有上下文都必须归属于当前 userId
2. 所有 prompt 注入前都要做权限过滤
3. deleted / archived / removed 数据不得注入 prompt
4. 敏感信息不默认保存为 memory
5. trace 只记录摘要和计数，不记录完整 prompt / secrets
6. RAG 检索必须复用已有 ScopeGuard，不允许绕过权限边界
```

一句话：

> **Agent Memory Mode 不是“能读更多东西”，而是“只能在权限允许范围内读更多上下文”。**
>
>

# 需要保护哪些对象？

这套系统里，权限对象不只是文档。

至少包括：

```Plain Text
conversation
conversation_message
conversation_summary
user_memory
knowledge_base
knowledge_base_document
rag evidence / citations
tool call result
context trace
```

也就是说，后端每次构建 prompt 时，不是简单查数据，而是要确认：

```Plain Text
这个 conversation 是不是当前用户的？
这个 summary 是不是当前 conversation 的？
这些 memory 是不是当前用户 ACTIVE 的？
这个 knowledgeBase 是不是当前用户的？
这些 RAG hits 是不是知识库 ACTIVE 文档里的？
这些 citations 会不会泄露别人的文档？
```

# Conversation 权限边界

`conversation` 是入口。

所有会话相关 API 都必须先校验：

```Plain Text
conversation.userId == currentUserId
```

包括：

```Plain Text
读取会话
发送消息
查看消息历史
查看摘要
删除摘要
绑定知识库
查看 context trace
```

不要让前端传 `userId`。

应该统一从登录态里拿：

```Plain Text
UserHolder.requireUserId()
```

也就是：

```Plain Text
用户请求 conversationId = 100
后端先查 conversation
如果 conversation.userId != currentUserId
直接拒绝
```

不要出现：

```Plain Text
select * from conversation where id = ?
```

而应该是：

```Plain Text
select * from conversation where id = ? and user_id = ?
```

# Message 权限边界

`conversation_message` 也不能只按 messageId 查。

因为用户可能伪造：

```Plain Text
GET /api/messages/999
```

所以查 message 时要通过 conversation owner 校验。

推荐方式：

```Plain Text
messageId -> 查 message
message.conversationId -> 查 conversation
conversation.userId == currentUserId
```

或者 SQL 直接 join：

```Plain Text
select m.*
from conversation_message m
join conversation c on m.conversation_id = c.id
where m.id = ?
  and c.user_id = ?
```

这样可以避免跨用户读取消息。

# Summary 权限边界

`conversation_summary` 是压缩后的历史上下文，虽然不是原始聊天，但仍然可能包含隐私和项目状态。

所以必须保证：

```Plain Text
summary.userId == currentUserId
summary.conversationId 属于 currentUserId
summary.status = ACTIVE
```

Deleted summary 不得注入 prompt：

```Plain Text
status = DELETED -> 不返回、不注入
status = FAILED -> 不注入，只降级 recent turns
status = GENERATING -> 不注入
status = ACTIVE -> 可注入
```

这里面试可以这样讲：

> 摘要虽然不是原文，但它是历史信息的压缩，同样要做 owner 校验和状态过滤。
>
>

# User Memory 权限边界

长期记忆是最高风险点。

因为它跨会话存在。

必须保证：

```Plain Text
memory.userId == currentUserId
memory.status = ACTIVE
```

用户只能：

```Plain Text
查看自己的 memory
删除自己的 memory
修改自己的 memory
注入自己的 memory
```

不能出现：

```Plain Text
Agent Memory Mode 注入了其他用户的偏好
```

API 上要这样设计：

```Plain Text
GET /api/memories
POST /api/memories
PATCH /api/memories/{memoryId}
DELETE /api/memories/{memoryId}
```

所有操作都加：

```Plain Text
where id = ? and user_id = currentUserId
```

删除建议软删除：

```Plain Text
ACTIVE -> DELETED
```

删除后的硬规则：

```Plain Text
DELETED memory 永远不能注入 prompt
DELETED memory 不出现在默认列表
DELETED memory 不参与 memory selector
```

# KnowledgeBase 权限边界

知识库绑定时必须校验：

```Plain Text
knowledgeBase.userId == currentUserId
knowledgeBase.status = ACTIVE
```

绑定会话时：

```Plain Text
conversation.userId == currentUserId
knowledgeBase.userId == currentUserId
```

也就是说，不能只更新：

```Plain Text
update conversation set bound_knowledge_base_id = ?
```

必须先确认这个知识库属于当前用户。

如果用户绑定别人的知识库：

```Plain Text
直接返回 FORBIDDEN
```

你的 T011 里已经设计了 `KnowledgeBaseScopeGuard`，用于校验知识库 owner、文档归属，并且只返回 ACTIVE 成员文档。
 所以这里不要重复造一套权限逻辑，应该复用：

```Plain Text
KnowledgeBaseScopeGuard.requireOwnedKnowledgeBase()
KnowledgeBaseScopeGuard.listActiveKnowledgeBaseDocuments()
```

# RAG Evidence / Citation 权限边界

RAG 是隐私泄露高发区。

因为用户可能看不到原文档，但通过模型回答和 citation 间接拿到内容。

所以 Agent Memory Mode 触发 RAG 时，必须保证：

```Plain Text
检索请求里带 userId
检索范围只包含 boundKnowledgeBase 的 ACTIVE documentIds
indexVersion 匹配
返回 hits 后二次 scope check
citations 也要做 scope check
```

不要直接从 Qdrant 查出来就拼 prompt。

正确链路是：

```Plain Text
ContextAssemblyService
-> KnowledgeBaseRagRetrievalService
-> KnowledgeBaseScopeGuard
-> VectorStoreClient.search(userId + documentIds + indexVersion)
-> post-filter scope check
-> evidence context
```

DocPilot 的 RAG 主线本来就强调 metadata filter、citation、Agent Trace / eval。

Agent Memory Mode 不能绕过这些已有机制。

# Prompt 注入前的统一过滤

我建议做一个统一的：

```Plain Text
ContextPermissionFilter
```

或者放在：

```Plain Text
ContextAssemblyService
```

里统一处理。

每个 `ContextItem` 注入 prompt 前都要有：

```Plain Text
ownerUserId
sourceType
sourceId
status
visibility
```

伪结构：

```Plain Text
ContextItem {
    ContextType type;        // MEMORY, SUMMARY, RECENT_TURN, RAG_EVIDENCE
    Long ownerUserId;
    String content;
    String sourceId;
    String status;
    boolean required;
}
```

注入前检查：

```Plain Text
ownerUserId == currentUserId
status == ACTIVE
content 不为空
没有被删除
没有超 token 预算
```

这样比各个 service 自己拼 prompt 安全。

# 敏感信息保存规则

长期记忆里不要默认保存敏感信息。

第一版建议规则：

```Plain Text
不保存 API key / token / 密码 / 连接串 / SSH 信息
不保存身份证、手机号、详细住址
不保存未经用户明确要求的健康、宗教、政治等敏感属性
不保存完整 .env 内容
不保存完整 prompt
```

用户如果输入：

```Plain Text
记住我的 API key 是 xxx
```

系统应该拒绝保存：

```Plain Text
这类密钥信息不适合保存到长期记忆中。
```

你可以把它设计成 memory 保存前的校验：

```Plain Text
MemorySafetyValidator
```

第一版可以用规则匹配：

```Plain Text
api_key
secret
password
token
Bearer
ssh
jdbc:
AKIA
.env
```

命中则拒绝保存或要求用户确认但不推荐保存。

# Trace 隐私边界

Trace 很有用，但不能太详细。

可以记录：

```Plain Text
contextMode
memoryCount
summaryUsed
recentTurnCount
ragTriggered
knowledgeBaseId
evidenceCount
citationDocumentIds
estimatedPromptTokens
```

不要记录：

```Plain Text
完整 prompt
完整 memory 内容
完整 summary 内容
完整 evidence 原文
API key
Authorization
连接串
异常堆栈
服务器 IP
```

也就是说，trace 是给调试和解释用的，不是把上下文原文全部暴露出来。

推荐 trace 示例：

```Plain Text
{
  "contextMode": "AGENT_MEMORY",
  "memoryCount": 3,
  "summaryUsed": true,
  "recentTurnCount": 8,
  "ragTriggered": true,
  "knowledgeBaseId": 12,
  "evidenceCount": 5,
  "documentHitCounts": {
    "ROADMAP_RAG.md": 2,
    "STATE.md": 1
  },
  "estimatedPromptTokens": 8200
}
```

# ToolCall 权限边界

如果 Agent Memory Mode 后续会调用工具，也要防止工具绕过权限。

比如：

```Plain Text
rag_qa_tool
knowledge_base_rag_tool
save_memory_tool
delete_memory_tool
bind_knowledge_base_tool
```

每个 tool 都不能相信模型给的 userId。

正确做法：

```Plain Text
userId 来自认证上下文
conversationId 来自当前会话
knowledgeBaseId 必须校验 owner
memoryId 必须校验 owner
documentId 必须校验 owner
```

也就是说：

> 模型可以提出“调用哪个工具、传什么参数”，但后端必须重新做权限校验。
>
>

# API 权限边界

建议每个 API 都遵守这个规则：

```Plain Text
不接受 body.userId
只从 UserHolder 获取 currentUserId
所有查询都加 userId 条件
所有修改都校验 owner
```

典型 API：

```Plain Text
POST /api/conversations
GET /api/conversations/{id}
POST /api/conversations/{id}/messages
GET /api/conversations/{id}/summary
DELETE /api/conversations/{id}/summary
POST /api/memories
GET /api/memories
DELETE /api/memories/{id}
PATCH /api/conversations/{id}/knowledge-base
```

全部必须围绕 currentUserId。

# 第一版 MVP 建议

第一版隐私与权限边界做到这些就够：

```Plain Text
1. conversation owner 校验
2. message 通过 conversation owner 校验
3. summary owner + status 校验
4. memory owner + ACTIVE 校验
5. deleted memory 不注入 prompt
6. knowledgeBase 绑定时校验 owner
7. RAG 检索复用 KnowledgeBaseScopeGuard
8. context trace 不返回完整 prompt
9. memory 保存前做敏感关键词规则拦截
10. 所有 API 不接受 body.userId
```

暂时不做：

```Plain Text
复杂隐私分类模型
自动敏感信息大模型审核
企业级审计平台
多租户 RBAC
团队共享知识库权限
memory 加密存储
```

这些后面可以扩展，但第一版不用做太大。

# 测试重点

必须覆盖：

```Plain Text
用户 A 不能读取用户 B 的 conversation
用户 A 不能读取用户 B 的 summary
用户 A 不能读取 / 删除用户 B 的 memory
DELETED memory 不注入 prompt
RECENT_TURNS 不注入 memory
AGENT_MEMORY 只注入当前用户 ACTIVE memory
用户不能绑定别人的 knowledgeBase
REMOVED KB document 不参与 RAG
RAG hits 跨用户 / 跨文档 / 跨版本被过滤
trace 不包含完整 prompt / secret
body.userId 被忽略或拒绝
```

这些测试比 UI 好不好看更重要。

# 面试怎么讲？

你可以这样讲：

> Agent Memory Mode 会读取会话摘要、长期记忆和绑定知识库 evidence，所以我把权限边界放在上下文组装层统一处理。所有上下文项注入 prompt 前都必须满足 ownerUserId 等于当前用户、状态为 ACTIVE，并且 deleted memory、removed knowledgeBase document 都不会进入 prompt。知识库 RAG 不直接查向量库，而是复用 KnowledgeBaseScopeGuard 和 RAG retrieval service，检索时使用 userId \+ documentIds \+ indexVersion 过滤，并对 hits 做二次 scope 校验。Trace 只记录 memoryCount、summaryUsed、ragTriggered、evidenceCount 等摘要信息，不保存完整 prompt、密钥、连接串或异常堆栈。
>
>

# 一句话定方案

我建议隐私与权限边界这样定：

> **Agent Memory Mode 的所有上下文来源都必须经过 userId owner 校验和状态过滤；长期记忆只注入当前用户 ACTIVE memory，知识库 RAG 复用 KnowledgeBaseScopeGuard，deleted / removed / forbidden 数据不得进入 prompt，trace 只记录脱敏摘要，不暴露完整 prompt 和敏感信息。**
>
>
