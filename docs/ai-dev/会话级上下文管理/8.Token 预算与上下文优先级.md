# 8\.Token 预算与上下文优先级

我们现在讨论 **8\. Token 预算与上下文优先级**。这一节是整个上下文管理系统里最工程化的一部分。

它解决的问题是：

> **Agent Memory Mode 会同时引入 recent turns、summary、memory、RAG evidence，如果不做预算，prompt 会越来越长，成本高、速度慢，还容易把模型注意力带偏。**
>
>

你前面的路线里也把这一节定义为：最近消息保留多少、summary 最多多少 token、memory 最多注入几条、RAG evidence 最多几条、超长时谁先被截断。

# 先定核心原则

我建议 Token 预算遵守 5 个原则：

```Plain Text
1. current user message 永远最高优先级，不能截断
2. system / safety rules 永远保留，不能截断
3. RAG evidence 在知识库问答中优先级高于 memory
4. recent turns 只保留最近几轮，旧消息交给 summary
5. memory 宁可少注入，也不要全部塞进去
```

一句话：

> **上下文不是越多越好，而是要把“当前问题最需要的信息”优先放进去。**
>
>

# 先区分两种预算

你要区分：

```Plain Text
模型总上下文窗口
实际 prompt 预算
```

比如模型支持 32k token，但你不能把 32k 都给 prompt。还要给回答留空间。

建议：

```Plain Text
modelContextLimit = 32000
reservedOutputTokens = 4000
maxPromptTokens = 24000
safetyBuffer = 4000
```

也就是：

```Plain Text
可用 prompt 预算 = 模型上下文窗口 - 预留回答 token - 安全 buffer
```

第一版可以不用特别精确，但后端要有这个概念。

# 两种模式的预算策略

## RECENT\_TURNS 标准模式

标准模式简单：

```Plain Text
System Prompt：固定保留
Recent Turns：最近 6～8 轮
Current Message：固定保留
```

建议第一版：

```Plain Text
recentTurnsMaxRounds = 8
recentTurnsMaxTokens = 4000
```

也就是说，标准模式不要 summary，不要 memory，不要 RAG evidence。

---

## AGENT\_MEMORY 记忆模式

Agent Memory Mode 才需要完整预算。

推荐第一版总预算：

```Plain Text
maxPromptTokens = 12000～16000
```

可以这样分：

第一版可以用更简单的配置：

```Plain Text
memoryMaxCount = 5
memoryMaxTokens = 800
summaryMaxTokens = 1200
recentTurnsMaxRounds = 8
recentTurnsMaxTokens = 4000
ragEvidenceMaxCount = 6
ragEvidenceMaxTokens = 6000
```

# 上下文优先级怎么排？

我建议定义 `ContextPriority`。

从高到低：

```Plain Text
P0：System / Safety Rules
P0：Current User Message
P1：Required RAG Evidence
P2：Recent Turns
P3：Conversation Summary
P4：User Memory
P5：Optional RAG Evidence
```

注意这里有一个关键点：

```Plain Text
requiredRag 和 optionalRag 优先级不同
```

如果用户明确说：

```Plain Text
根据知识库回答
结合文档内容回答
```

那 RAG evidence 是 Required，优先级很高。

如果只是系统觉得可能有帮助，RAG evidence 是 Optional，预算不足可以少放甚至不放。

# 超长时谁先被截断？

我建议裁剪顺序是：

```Plain Text
1. 先减少 optional RAG evidence 数量
2. 再减少 memory 数量
3. 再裁剪 summary 长度
4. 再减少 older recent turns
5. 再裁剪 required RAG evidence 的尾部内容
6. 永不裁剪 current user message 和 system safety rules
```

但如果是明确的知识库问答，裁剪顺序要稍微变：

```Plain Text
1. 先减少 memory
2. 再裁剪 summary
3. 再减少 older recent turns
4. 最后裁剪 RAG evidence
```

原因是：用户要求“根据资料回答”时，证据比用户偏好更重要。



# Recent Turns 保留多少？

第一版建议：

```Plain Text
标准模式：最近 8 轮
Agent Memory Mode：最近 6～8 轮
```

这里的“一轮”指：

```Plain Text
user + assistant
```

不要保留太多。

长对话的旧内容应该进入 summary，而不是继续塞 recent turns。

如果超 token：

```Plain Text
先删最旧的一轮
保留最近的一轮
当前用户消息单独保留，不算在 recent turns 里
```

# Summary 最多多少 token？

建议：

```Plain Text
summaryMaxTokens = 1200
```

如果摘要太长，说明摘要机制本身失败了。

摘要应该是结构化的：

```Plain Text
当前主题
已确定决策
当前进度
待解决问题
重要约束
```

而不是把历史对话重新写一遍。

超长时可以二次压缩：

```Plain Text
compressSummary(summary, targetTokens = 1000)
```

第一版也可以简单截断，但更推荐重新摘要。

# Memory 最多注入几条？

第一版建议：

```Plain Text
memoryMaxCount = 3～5
memoryMaxTokens = 800
```

排序规则：

```Plain Text
1. 当前项目相关 PROJECT_STATE
2. 用户回答风格 PREFERENCE / ANSWER_STYLE
3. 当前求职目标 TASK_GOAL
4. 技术上下文 TECH_CONTEXT
5. 最近更新的 CUSTOM
```

不要把所有 memory 都塞进去。

长期记忆的目标是“辅助回答”，不是“占满 prompt”。



# RAG Evidence 最多几条？

结合你现在的知识库 RAG，第一版建议：

```Plain Text
topK = 6
ragEvidenceMaxCount = 6
ragEvidenceMaxTokens = 6000
单条 evidence snippet 500～800 token
```

如果是资料集总结类问题，可以保证多文档覆盖：

```Plain Text
每篇文档最多 1～2 条 evidence
优先覆盖更多 documentTitle
```

DocPilot 的 RAG 主线本身已经把 prompt 上下文构造、citation 引用证据、Agent Trace / eval 记录作为完整链路的一部分。

所以 evidence 不只是给模型看的，也要能对应 citation 和 trace。

# 推荐的 ContextItem 结构

后端可以统一抽象：

```Plain Text
public record ContextItem(
    ContextType type,
    String content,
    int priority,
    int estimatedTokens,
    boolean required,
    String sourceId,
    Map<String, Object> metadata
) {}
```

`ContextType`：

```Plain Text
SYSTEM
MODE_INSTRUCTION
MEMORY
SUMMARY
RECENT_TURN
RAG_EVIDENCE
CURRENT_MESSAGE
OUTPUT_REQUIREMENT
```

然后统一交给：

```Plain Text
TokenBudgetManager
```

处理。

# TokenBudgetManager 逻辑

伪流程：

```Plain Text
1. 收集所有 ContextItem
2. 标记 required / optional
3. 估算 token
4. 先放 required item
5. 再按优先级放 optional item
6. 如果超限，按裁剪策略移除或截断
7. 输出 final context + contextTrace
```

注意：第一版不一定要精确 token 计算。

可以先做：

```Plain Text
中文：按字符数粗略估算
英文：按 words / 0.75 粗略估算
```

后续再替换成模型 tokenizer。

# Prompt 拼接后的 trace

每次回答应该记录：

```Plain Text
{
  "contextMode": "AGENT_MEMORY",
  "maxPromptTokens": 12000,
  "estimatedPromptTokens": 8600,
  "summaryTokens": 900,
  "memoryCount": 4,
  "memoryTokens": 520,
  "recentTurnCount": 8,
  "recentTurnTokens": 3200,
  "ragTriggered": true,
  "ragEvidenceCount": 6,
  "ragEvidenceTokens": 3900,
  "truncatedTypes": ["OLDER_RECENT_TURNS"],
  "currentMessageTokens": 300
}
```

trace 不要记录完整 prompt，也不要记录敏感信息。你项目环境边界里本来也强调不上传 `.env`、API key、SSH 信息、数据库密码、真实 token，本地测试也不应该强依赖远程服务器。

# MVP 配置建议

第一版直接写成配置类：

```Plain Text
ContextBudgetProperties {
    int maxPromptTokens = 12000;
    int reservedOutputTokens = 3000;

    int recentTurnsMaxRounds = 8;
    int recentTurnsMaxTokens = 4000;

    int summaryMaxTokens = 1200;

    int memoryMaxCount = 5;
    int memoryMaxTokens = 800;

    int ragEvidenceMaxCount = 6;
    int ragEvidenceMaxTokens = 6000;

    int singleEvidenceMaxTokens = 800;
}
```

这样后续可以改配置，不用改代码。

# 不同场景下的优先级

## 普通追问

例如：

```Plain Text
继续说
换成面试版
```

优先级：

```Plain Text
current message
recent turns
summary
memory
```

不触发 RAG。

---

## 项目协作

例如：

```Plain Text
按照之前路线继续设计下一步
```

优先级：

```Plain Text
current message
summary
recent turns
project memory
```

不一定触发 RAG。

---

## 知识库问答

例如：

```Plain Text
根据资料集总结这几篇文档
```

优先级：

```Plain Text
current message
RAG evidence
recent turns
summary
memory
```

这里 evidence 优先级高。

---

## 用户偏好类回答

例如：

```Plain Text
按我平时喜欢的方式解释这个问题
```

优先级：

```Plain Text
current message
memory
recent turns
summary
```

# 测试重点

必须测：

```Plain Text
RECENT_TURNS 不注入 summary / memory / RAG
AGENT_MEMORY 注入 summary + memory
RAG 触发时 evidence 进入 prompt
超过 maxPromptTokens 时先裁剪低优先级上下文
current user message 不被裁剪
system prompt 不被裁剪
memory 注入数量不超过 memoryMaxCount
summary 超长时被压缩或截断
RAG evidence 不超过 ragEvidenceMaxCount
trace 正确记录 token 估算和截断类型
```

---

# 面试怎么讲？

你可以这样讲：

> 我没有把会话历史、记忆和 RAG 证据无限塞进 prompt，而是设计了 TokenBudgetManager。每类上下文都会被封装成 ContextItem，包含 type、priority、estimatedTokens 和 required 标记。系统先保留 system rules 和 current user message，再根据模式和问题类型选择 recent turns、summary、memory 和 RAG evidence。普通追问优先 recent turns，知识库问答优先 RAG evidence；超过预算时按优先级裁剪 older recent turns、memory、summary 或 optional evidence，并在 trace 中记录各类上下文的 token 估算和截断情况。
>
>

---

# 一句话定方案

我建议 Token 预算与上下文优先级这样定：

> **用 TokenBudgetManager 统一管理上下文预算：current message 和 system rules 必保留；RECENT\_TURNS 只保留最近 6～8 轮；AGENT\_MEMORY 下限制 summary、memory、RAG evidence 的 token 和数量；知识库问答优先保留 RAG evidence，普通追问优先保留 recent turns，超长时按优先级裁剪并记录 context trace。**
>
>
