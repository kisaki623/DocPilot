# 2\.数据模型设计

# 总体表设计

我建议第一版设计 6 张表：

```Plain Text
tb_conversation
tb_conversation_message
tb_conversation_summary
tb_user_memory
tb_conversation_knowledge_binding
tb_context_assembly_trace
```

其中 MVP 必做：

```Plain Text
tb_conversation
tb_conversation_message
tb_conversation_summary
tb_user_memory
```

后续增强再做：

```Plain Text
tb_conversation_knowledge_binding
tb_context_assembly_trace
```

# tb\_conversation：会话主表

这张表是整个功能的核心。

它表示一个用户创建的一次对话。

```Plain Text
tb_conversation
- id
- user_id
- title
- context_mode
- status
- bound_knowledge_base_id
- summary_enabled
- memory_enabled
- last_message_time
- create_time
- update_time
```

## 关键字段解释

### context\_mode

最重要。

```Plain Text
RECENT_TURNS
AGENT_MEMORY
```

含义：

```Plain Text
RECENT_TURNS：标准对话，只带最近多轮
AGENT_MEMORY：记忆对话，带最近多轮 + 摘要 + 长期记忆 + 可选知识库
```

这个字段建议**创建会话时确定，创建后默认固定**。

---

### bound\_knowledge\_base\_id

表示这个会话是否绑定某个知识库。

```Plain Text
null：不绑定知识库
有值：Agent Memory Mode 下可以结合该知识库做 RAG
```

注意：绑定时必须校验这个知识库属于当前用户。你已有 KnowledgeBaseScopeGuard 的思路，可以复用类似设计。

---

### summary\_enabled / memory\_enabled

这两个字段用于更细粒度控制。

例如：

```Plain Text
RECENT_TURNS：summary_enabled=false, memory_enabled=false
AGENT_MEMORY：summary_enabled=true, memory_enabled=true
```

以后如果用户想关闭记忆但保留摘要，也有扩展空间。

---

## 推荐索引

```Plain Text
idx_conversation_user_id(user_id)
idx_conversation_user_status(user_id, status)
idx_conversation_last_message_time(last_message_time)
```

如果你允许同名会话，不需要唯一索引。

如果你想防止重复标题，可以加：

```Plain Text
uk_conversation_user_title(user_id, title)
```

但我不建议加，因为聊天会话标题重复很正常。

# tb\_conversation\_message：消息表

这张表存原始聊天消息。

```Plain Text
tb_conversation_message
- id
- conversation_id
- user_id
- role
- content
- token_count
- sequence_no
- status
- create_time
```

## role

建议枚举：

```Plain Text
USER
ASSISTANT
SYSTEM
TOOL
```

以后如果你接 ToolCall / Function Calling，这个 `TOOL` 会有用。

你现在的 RAG 主线本来就有 Agent Trace / eval 记录目标，RAG 闭环里也包含 Agent Trace / eval 记录。
 所以消息表提前支持 `TOOL` 是合理的。

---

## sequence\_no

这个字段很重要。

不要只靠 create\_time 排序。

建议每个 conversation 内部维护递增序号：

```Plain Text
1, 2, 3, 4...
```

这样取最近 N 轮时更稳定：

```Plain Text
where conversation_id = ?
order by sequence_no desc
limit ?
```

---

## token\_count

用于上下文预算。

你后面做 ContextAssemblyService 时，需要知道：

```Plain Text
最近多轮用了多少 token
summary 用了多少 token
memory 用了多少 token
RAG evidence 用了多少 token
```

第一版可以粗略估算，不一定精确。

---

## 推荐索引

```Plain Text
idx_message_conversation_seq(conversation_id, sequence_no)
idx_message_user_conversation(user_id, conversation_id)
idx_message_create_time(create_time)
```

# tb\_conversation\_summary：会话摘要表

这张表解决长对话不能全塞 prompt 的问题。

```Plain Text
tb_conversation_summary
- id
- conversation_id
- user_id
- summary
- covered_start_seq
- covered_end_seq
- summary_version
- status
- create_time
- update_time
```

## covered\_start\_seq / covered\_end\_seq

表示这段摘要覆盖哪些消息。

例如：

```Plain Text
summary 覆盖第 1～30 条消息
最近多轮保留第 31～40 条消息
```

最终 prompt 是：

```Plain Text
summary(1～30)
+ recent messages(31～40)
+ current question
```

这样既保留长期上下文，又不会把全部历史塞进去。

---

## summary\_version

用于以后摘要策略升级。

比如：

```Plain Text
v1：普通摘要
v2：任务状态摘要
v3：按用户偏好/项目进度结构化摘要
```

---

## status

```Plain Text
ACTIVE
STALE
DELETED
```

当新消息超过一定数量后，旧 summary 可以标记为 `STALE`，然后后台重新生成。

---

## 推荐索引

```Plain Text
idx_summary_conversation(conversation_id)
idx_summary_user_conversation(user_id, conversation_id)
```

# tb\_user\_memory：长期记忆表

这张表存跨会话可复用的用户记忆。

```Plain Text
tb_user_memory
- id
- user_id
- memory_type
- content
- source_type
- source_conversation_id
- source_message_id
- status
- priority
- confidence
- create_time
- update_time
```

## memory\_type

建议第一版用这些：

```Plain Text
PREFERENCE       用户偏好
PROJECT_STATE    项目状态
TASK_GOAL        任务目标
STYLE            回答风格
CUSTOM           用户手动保存的自定义记忆
```

例如：

```Plain Text
PREFERENCE：用户希望回答偏面试导向
PROJECT_STATE：DocPilot 当前已完成 T012
TASK_GOAL：用户当前目标是找 Java 后端 / AI 应用实习
STYLE：用户喜欢先讲结论再解释
```

---

## source\_type

建议：

```Plain Text
MANUAL
ASSISTANT_SUGGESTED
SYSTEM_EXTRACTED
```

第一版建议只做：

```Plain Text
MANUAL
```

也就是用户主动点“记住这个”才保存。

不要一开始就做自动抽取，否则会带来误记、隐私、删除、冲突等复杂问题。

---

## priority / confidence

这两个字段可以第一版保留，但不一定强依赖。

```Plain Text
priority：越高越优先注入 prompt
confidence：记忆可信度
```

第一版默认：

```Plain Text
priority = 0
confidence = 1.0
```

---

## status

```Plain Text
ACTIVE
DELETED
DISABLED
```

用户删除记忆后，不要物理删除，先软删除：

```Plain Text
ACTIVE -> DELETED
```

后续上下文注入必须过滤：

```Plain Text
where status = 'ACTIVE'
```

这和你 KnowledgeBaseDocument 软删除思路一致。

---

## 推荐索引

```Plain Text
idx_memory_user_status(user_id, status)
idx_memory_user_type(user_id, memory_type)
idx_memory_source_conversation(source_conversation_id)
```

# tb\_conversation\_knowledge\_binding：会话知识库绑定表

如果你只允许一个会话绑定一个知识库，可以直接放在 `tb_conversation.bound_knowledge_base_id`。

但如果你以后想支持多个知识库，就单独建表：

```Plain Text
tb_conversation_knowledge_binding
- id
- conversation_id
- user_id
- knowledge_base_id
- status
- create_time
- update_time
```

## 第一版建议

我建议第一版先简单点：

```Plain Text
tb_conversation.bound_knowledge_base_id
```

不单独建绑定表。

原因是：

```Plain Text
实现简单
权限容易校验
Agent Memory Mode 第一版够用
```

后续要支持多个知识库时，再迁移到关系表。

# tb\_context\_assembly\_trace：上下文组装追踪表

这张表不是第一版必须，但很适合做亮点。

它记录某次回答到底用了哪些上下文。

```Plain Text
tb_context_assembly_trace
- id
- conversation_id
- message_id
- user_id
- context_mode
- recent_message_count
- used_summary
- used_memory_count
- used_knowledge_base_id
- used_rag
- rag_hit_count
- estimated_prompt_tokens
- create_time
```

## 作用

它能解释：

```Plain Text
本轮回答用了最近几轮？
有没有用 summary？
注入了几条 memory？
有没有触发 RAG？
命中了几个文档？
prompt 大概多少 token？
```

这对调试和面试都很有用。

前端以后可以展示：

```Plain Text
本轮上下文：最近 8 条消息 + 会话摘要 + 3 条记忆 + 4 条知识库证据
```

这个很像真实 AI 产品。

# 表之间的关系

整体关系是：

```Plain Text
user
 ├── tb_conversation
 │     ├── tb_conversation_message
 │     ├── tb_conversation_summary
 │     └── tb_context_assembly_trace
 │
 ├── tb_user_memory
 │
 └── tb_knowledge_base
        └── tb_knowledge_base_document
```

也就是说：

```Plain Text
conversation 负责当前会话
message 负责原始消息
summary 负责压缩历史
user_memory 负责跨会话长期记忆
knowledge_base 负责文档资料
trace 负责解释本轮用了什么上下文
```

# 这个数据模型的核心设计原则

你后面设计时记住 5 个原则：

```Plain Text
1. 所有表都带 user_id，方便权限隔离
2. conversation.context_mode 决定上下文策略
3. 原始消息和摘要分开存
4. 长期记忆必须可删除、可禁用
5. 知识库绑定不能绕过 KnowledgeBaseScopeGuard
```

这 5 点是面试时最容易讲出工程深度的。

---

# 最终推荐版本

我建议你把数据模型定成：

```Plain Text
核心会话层：
- tb_conversation
- tb_conversation_message

压缩上下文层：
- tb_conversation_summary

长期记忆层：
- tb_user_memory

知识库融合层：
- tb_conversation.bound_knowledge_base_id
  第一版先不单独建 binding 表

可观测层：
- tb_context_assembly_trace
  第一版可选，后续增强
```

一句话定义：

> **以 conversation 为主线，用 message 保存原始多轮，用 summary 压缩长上下文，用 user\_memory 保存跨会话长期偏好，用 bound\_knowledge\_base\_id 接入知识库 RAG，再用 trace 解释每轮回答使用了哪些上下文。**
>
>
