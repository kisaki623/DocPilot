# 9\.上下文构建服务设计

现在开始 **9\. 上下文构建服务设计**。这一节的核心是：

> 把前面讨论的产品模式、摘要、长期记忆、RAG、权限、token 预算，统一收束成后端的一套核心服务。
>
>

也就是说，前面 1～8 是规则；第 9 步是把这些规则变成后端架构。

# 这个模块的定位

我建议把核心服务命名为：

```Plain Text
ContextAssemblyService
```

中文叫：

```Plain Text
上下文组装服务
```

它负责的事情是：

```Plain Text
用户发来一条消息
-> 根据 conversation.contextMode 判断模式
-> 加载最近消息 / 摘要 / 长期记忆 / RAG evidence
-> 做权限过滤
-> 做 token 预算裁剪
-> 拼成最终 prompt
-> 输出 contextTrace
```

它不是直接回答问题的服务。

它只负责：

> **给大模型准备上下文。**
>
>

# 整体调用链路

推荐后端主链路是：

```Plain Text
ConversationController
-> ConversationService
-> ContextAssemblyService
-> AiAnswerService / RagQaService
-> 保存 assistant message
-> 返回 answer + contextTrace
```

更细一点：

```Plain Text
用户发送消息
-> 保存 user message
-> ContextAssemblyService.buildContext()
-> 得到 promptMessages / contextItems / trace
-> 调用模型生成回答
-> 保存 assistant message
-> maybeScheduleSummary()
-> 返回结果
```

注意：

不要让 Controller 自己拼 prompt，也不要让 Agent / QA / Memory 各自拼一套 prompt。

核心拼接逻辑应该集中到：

```Plain Text
ContextAssemblyService
```

# 核心输入输出设计

## 输入：ContextAssemblyRequest

可以设计成：

```Plain Text
ContextAssemblyRequest {
    Long userId;
    Long conversationId;
    String currentMessage;
    ContextMode contextMode;
    Long boundKnowledgeBaseId;
    String sessionId;
    Integer maxPromptTokens;
}
```

核心字段解释：

```Plain Text
userId：当前登录用户
conversationId：当前会话
currentMessage：当前用户问题
contextMode：RECENT_TURNS / AGENT_MEMORY
boundKnowledgeBaseId：可选，Agent Memory Mode 下可能使用
maxPromptTokens：本轮 prompt 最大预算
```

---

## 输出：ContextAssemblyResult

建议输出不要只是一段字符串，而是结构化对象：

```Plain Text
ContextAssemblyResult {
    List<PromptMessage> promptMessages;
    List<ContextItem> usedItems;
    ContextTrace trace;
    boolean ragTriggered;
    boolean ragRequired;
    List<Citation> citations;
}
```

原因是：

```Plain Text
promptMessages 给模型用
usedItems 给调试和测试用
trace 给前端和日志用
citations 给回答引用用
```

不要只返回一个大 prompt 字符串。否则后续 trace、测试、裁剪都不好做。

# 核心对象：ContextItem

我建议统一抽象一个：

```Plain Text
ContextItem
```

它表示“准备放进 prompt 的一段上下文”。

字段：

```Plain Text
ContextItem {
    ContextType type;
    String content;
    int priority;
    int estimatedTokens;
    boolean required;
    Long ownerUserId;
    String sourceId;
    Map<String, Object> metadata;
}
```

`ContextType` 可以有：

```Plain Text
SYSTEM
MODE_INSTRUCTION
MEMORY
SUMMARY
RECENT_TURN
RAG_EVIDENCE
CURRENT_MESSAGE
OUTPUT_REQUIREMENT
```

这样所有上下文都变成统一对象。

好处是：

```Plain Text
可以统一权限过滤
可以统一 token 估算
可以统一排序裁剪
可以统一 trace
```

# 核心服务拆分

我建议第 9 步设计成这些组件。

---

## 5\.1 ContextAssemblyService：总入口

职责：

```Plain Text
根据 conversationId 和 currentMessage 构建最终上下文
```

它不应该直接写很多细节，而是编排其他组件。

伪流程：

```Plain Text
1. 校验 conversation 属于 userId
2. 读取 conversation.contextMode
3. 根据模式选择 ContextBuilder
4. 收集 ContextItem
5. 权限过滤
6. token 预算裁剪
7. 渲染成 promptMessages
8. 生成 contextTrace
9. 返回 ContextAssemblyResult
```

---

## 5\.2 ContextPolicy：策略决策

职责：

```Plain Text
决定当前会话应该用什么上下文策略
```

它回答这些问题：

```Plain Text
当前是 RECENT_TURNS 还是 AGENT_MEMORY？
是否允许使用 summary？
是否允许注入 memory？
是否允许触发 RAG？
recent turns 保留多少？
token budget 是多少？
```

可以设计：

```Plain Text
ContextPolicy {
    ContextMode mode;
    int recentTurnsMaxRounds;
    int memoryMaxCount;
    int summaryMaxTokens;
    int ragEvidenceMaxCount;
    int maxPromptTokens;
}
```

第一版 `ContextPolicy` 可以很简单，直接根据 `contextMode` 返回固定配置。

---

## 5\.3 RecentTurnsContextBuilder

职责：

```Plain Text
构建最近多轮消息上下文
```

输入：

```Plain Text
userId
conversationId
maxRounds
maxTokens
```

输出：

```Plain Text
List<ContextItem>
```

规则：

```Plain Text
只读取当前用户自己的 conversation messages
按时间倒序取最近 N 轮
再正序拼回 prompt
不包含当前 user message
```

标准模式主要靠它。

---

## 5\.4 AgentMemoryContextBuilder

职责：

```Plain Text
构建 Agent Memory Mode 下的增强上下文
```

它不是直接查所有东西，而是编排：

```Plain Text
MemorySelector
ConversationSummaryService
RecentTurnsContextBuilder
KnowledgeBaseEvidenceBuilder
```

输出：

```Plain Text
memory items
summary item
recent turn items
rag evidence items
```

可以理解成：

```Plain Text
AgentMemoryContextBuilder = Agent 模式上下文收集器
```

---

## 5\.5 MemorySelector

职责：

```Plain Text
从 user_memory 中选择本轮要注入的长期记忆
```

规则：

```Plain Text
只取当前 userId
只取 ACTIVE
最多 3～5 条
按 priority / type / updatedTime 排序
不取 DELETED / ARCHIVED
```

第一版不做 embedding 检索，直接按类型和优先级选。

推荐优先级：

```Plain Text
PROJECT_STATE
PREFERENCE / ANSWER_STYLE
TASK_GOAL
TECH_CONTEXT
CUSTOM
```

---

## 5\.6 ConversationSummaryService

职责：

```Plain Text
读取、生成、更新会话摘要
```

在上下文构建里只做一件事：

```Plain Text
getActiveSummary(userId, conversationId)
```

返回 ACTIVE summary。

如果 summary 不存在或 FAILED：

```Plain Text
返回空，不影响回答
```

摘要生成可以在回答后异步做，不放在 ContextAssemblyService 里同步做。

---

## 5\.7 KnowledgeBaseEvidenceBuilder

职责：

```Plain Text
判断是否需要 RAG，并获取知识库 evidence
```

它不直接查 Qdrant，而是调用已有的：

```Plain Text
KnowledgeBaseRagRetrievalService
```

流程：

```Plain Text
1. 判断 conversation 是否绑定 knowledgeBaseId
2. 判断当前问题是否需要 RAG
3. 如果需要，调用 KnowledgeBaseRagRetrievalService
4. 把 retrieval hits 转成 RAG_EVIDENCE ContextItem
```

重要规则：

```Plain Text
RECENT_TURNS 模式不触发 RAG
AGENT_MEMORY + boundKnowledgeBaseId 才可能触发 RAG
requiredRag no-evidence 返回 fallback
optionalRag no-evidence 可以降级
```

---

## 5\.8 ContextPermissionFilter

职责：

```Plain Text
所有 ContextItem 注入 prompt 前做权限过滤
```

检查：

```Plain Text
ownerUserId == currentUserId
status == ACTIVE
content 非空
source 未删除
```

对 RAG evidence：

```Plain Text
必须已经通过 KnowledgeBaseScopeGuard / RagScopeGuard
```

这里的意义是：

> 不允许任何 memory、summary、message、evidence 绕过 owner 校验直接进入 prompt。
>
>

---

## 5\.9 TokenBudgetManager

职责：

```Plain Text
根据 token 预算裁剪 ContextItem
```

流程：

```Plain Text
1. required items 先保留
2. optional items 按 priority 排序
3. 超限时按裁剪规则移除
4. 记录 truncatedTypes
```

永远不能裁剪：

```Plain Text
SYSTEM
CURRENT_MESSAGE
```

知识库问答时优先保留：

```Plain Text
RAG_EVIDENCE
```

普通追问时优先保留：

```Plain Text
RECENT_TURN
```

---

## 5\.10 PromptRenderer

职责：

```Plain Text
把 ContextItem 渲染成 PromptMessage
```

比如渲染成：

```Plain Text
system message
user memory block
conversation summary block
recent turns block
knowledge evidence block
current question block
```

不要让每个 builder 自己拼最终 prompt。

推荐：

```Plain Text
ContextItem -> PromptRenderer -> List<PromptMessage>
```

---

## 5\.11 ContextTraceBuilder

职责：

```Plain Text
根据 usedItems 和裁剪结果生成 trace
```

trace 包括：

```Plain Text
contextMode
summaryUsed
memoryCount
recentTurnCount
ragTriggered
evidenceCount
estimatedPromptTokens
truncatedTypes
```

不包含：

```Plain Text
完整 prompt
完整 memory
完整 summary
完整 evidence 原文
secret
异常堆栈
```

# 两种模式的执行流程

## RECENT\_TURNS 模式

```Plain Text
ContextAssemblyService
-> ContextPolicy(mode=RECENT_TURNS)
-> System ContextItem
-> ModeInstruction ContextItem
-> RecentTurnsContextBuilder
-> CurrentMessage ContextItem
-> ContextPermissionFilter
-> TokenBudgetManager
-> PromptRenderer
-> ContextTraceBuilder
```

不会调用：

```Plain Text
MemorySelector
ConversationSummaryService
KnowledgeBaseEvidenceBuilder
```

也就是：

```Plain Text
标准模式保持轻量。
```

---

## AGENT\_MEMORY 模式

```Plain Text
ContextAssemblyService
-> ContextPolicy(mode=AGENT_MEMORY)
-> System ContextItem
-> ModeInstruction ContextItem
-> MemorySelector
-> ConversationSummaryService
-> RecentTurnsContextBuilder
-> KnowledgeBaseEvidenceBuilder，可选
-> CurrentMessage ContextItem
-> ContextPermissionFilter
-> TokenBudgetManager
-> PromptRenderer
-> ContextTraceBuilder
```

这就是完整增强模式。

# 服务之间的关系图

可以这样理解：

```Plain Text
ContextAssemblyService
    |
    |-- ContextPolicy
    |
    |-- RecentTurnsContextBuilder
    |
    |-- AgentMemoryContextBuilder
          |-- MemorySelector
          |-- ConversationSummaryService
          |-- RecentTurnsContextBuilder
          |-- KnowledgeBaseEvidenceBuilder
                |-- KnowledgeBaseRagRetrievalService
    |
    |-- ContextPermissionFilter
    |
    |-- TokenBudgetManager
    |
    |-- PromptRenderer
    |
    |-- ContextTraceBuilder
```

一句话：

> ContextAssemblyService 是总调度，其他组件各做一件小事。
>
>

# 第一版 MVP 推荐

第一版不要做太大。

做到这些就够：

```Plain Text
1. ContextAssemblyService
2. ContextItem / ContextType
3. ContextPolicy
4. RecentTurnsContextBuilder
5. AgentMemoryContextBuilder
6. MemorySelector
7. ConversationSummaryService.getActiveSummary
8. KnowledgeBaseEvidenceBuilder
9. TokenBudgetManager
10. PromptRenderer
11. ContextTrace
```

但是实现范围可以收缩：

```Plain Text
RECENT_TURNS：只拼 system + recent turns + current message
AGENT_MEMORY：拼 system + memory + summary + recent turns + optional RAG evidence + current message
```

暂时不做：

```Plain Text
复杂 intent classifier
复杂 memory embedding 检索
多知识库自动选择
多版本 prompt 模板
复杂 tokenizer
```

# 关键设计取舍

## 取舍一：ContextAssemblyService 返回 prompt 还是返回 ContextItem？

建议：

```Plain Text
两个都返回。
```

也就是：

```Plain Text
ContextAssemblyResult.promptMessages
ContextAssemblyResult.usedItems
```

原因：

```Plain Text
promptMessages 给模型用
usedItems 给测试和 trace 用
```

---

## 取舍二：RAG 在 ContextAssemblyService 里做，还是在 QA Service 里做？

对 Agent Memory Mode 来说，建议：

```Plain Text
ContextAssemblyService 负责触发 RAG evidence 获取
```

但它不能直接查向量库，只能调用：

```Plain Text
KnowledgeBaseRagRetrievalService
```

这样好处是：

```Plain Text
上下文拼接统一
RAG evidence 可以和 memory / summary 一起预算
权限逻辑复用已有 service
```

---

## 取舍三：权限过滤放在每个 builder，还是统一 filter？

建议：

```Plain Text
两层都要有。
```

具体是：

```Plain Text
builder 查数据时必须按 userId 查
ContextPermissionFilter 注入前再兜底检查
```

这叫防御式设计。

# 面试怎么讲？

你可以这样讲：

> 我把上下文构建抽象成 ContextAssemblyService，它不直接回答问题，而是负责根据 conversation 的 contextMode 构建 prompt。标准模式只加载最近多轮；Agent Memory Mode 会额外加载用户长期记忆、会话摘要和可选知识库 evidence。所有上下文都会统一抽象成 ContextItem，包含 type、priority、estimatedTokens、required 和 source metadata，然后经过权限过滤、TokenBudgetManager 裁剪，最后由 PromptRenderer 渲染成模型消息，同时生成 ContextTrace 用于调试和前端展示。这样避免各个业务 service 分散拼 prompt，也方便测试和后续扩展。
>
>

---

# 一句话定方案

我建议上下文构建服务这样定：

> **以 ContextAssemblyService 作为统一入口，按 RECENT\_TURNS / AGENT\_MEMORY 选择不同 builder，把 system、memory、summary、recent turns、RAG evidence、current message 统一抽象为 ContextItem，再经过权限过滤、token 预算裁剪和 PromptRenderer 生成最终 prompt，同时输出 ContextTrace。**
>
>
